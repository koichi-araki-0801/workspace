本書は Editor を運用端末に構築し、運用するための手順を、情報システム担当向けにまとめる。内部構造は別冊「Editor 詳細設計書」を参照。rest モード（REST + SQL Server。既定）と local モード（fixtures + localStorage。開発用）の両方を扱う。

# 1. 構成方針

- **PDF 生成はサーバ側に集約**（運用端末 1 台）。ブラウザは社内 Windows の Microsoft Edge を使う（Chromium 同梱なし）。
- **依存はオフライン調達**: pnpm オフラインストア（`.pnpm-store/`）を tar.gz で持ち込み、運用端末で復元する。
- フォントは @fontsource でローカル同梱（Google Fonts CDN 非依存）。
- 前提: パッケージマネージャ `pnpm@11.18.0+`、Node `>=24`。

> [!WARN] 調達端末と運用端末は **Windows x64・Node 24 で一致**させること（msnodesqlv8 等のネイティブバイナリが必要）。

# 2. オフライン調達・展開

1. **調達**: 配布担当の端末で重量物バンドルを生成し GitHub Releases へ置く（git 管理外の `local-only/offline-publish/`。依存を変えたら手動で実行する）。
2. **持ち込み・展開**: 運用端末の多くは `git clone` できない。ネットに出られる端末で `offline/fetch-offline-bundle.bat -Source` を実行し、Release から重量物バンドルとソース ZIP（`source.zip` / `.sha256`）を合わせて取得する。取得した 5 ファイル（`offline-deps-bundle.tar.gz` / `.sha256` / `bundle.key` / `source.zip` / `source.zip.sha256`）を運用端末へ持ち込み、初回は `source.zip` を新しいフォルダへ展開し、重量物 3 ファイルをその直下へ置いてから `offline/setup-offline.bat` を実行し、更新は新しい `source.zip` を直下に置いて同じ `offline/setup-offline.bat` を再実行する（setup が旧版の削除・展開・構築までを完走させる）。`git clone` できる端末では、リポジトリを clone したうえで `offline/fetch-offline-bundle.bat` → `offline/setup-offline.bat` の順に実行すればよい（source.zip の展開は不要）。いずれの経路も setup は取得を行わず、ネイティブバイナリの追加取得も走らないこと。
3. **検証**: 5 章のチェックリストを実施する。

`paths.assetsDir` は廃止した。appconfig に残っていると、不明なキーとして読み込みエラーになり起動しない（フォント移設パッチ `editor/patches/2026-10-fonts-to-css/` が `paths.jsDir` へ置き換える）。環境変数 `ASSETS_DIR` は読まない（設定されていても何も起きないので、手で外す）。フォントは `paths.cssDir` の下の `fonts/` に、js は `paths.jsDir` に置く。

旧構成（`<dataRoot>\assets`、CSS の `url(../fonts/…)`）が残っていても起動は止まらず、起動ログに次の警告が出る（左の列は各ログ行の先頭部分の引用）。そのまま使うと、フォントと JS が欠けた PDF が成功扱いで出る。

| 起動ログ（…で始まる行） | 意味と対応 |
|---|---|
| `[layout] 旧構成の … が残っています` | `<dataRoot>\assets` が残っている。フォント移設パッチ（`editor/patches/2026-10-fonts-to-css/`）を流す |
| `[layout] … の CSS に url(../fonts/ が残っています` | `paths.cssDir` 直下の CSS が旧い書き方のまま（括弧の中に該当するファイル名が 5 件まで出る）。フォント移設パッチを流す |
| `[layout] 旧構成の確認に失敗しました` | 確認そのものが失敗した（置き場の読み取り権限など）。起動は続く。メッセージの原因を確かめる |

## 3.1 data リポジトリをファイルサーバの共有へ置く

テンプレート実体（`dataRoot`）は、UNC パス（`\\fileserver\share\editor-data` など）の共有フォルダへ置ける。コードの変更は要らず、環境変数 `DATA_ROOT` を向けるだけで切り替わる。置くのは `dataRoot` **全体**とする。`filled/` だけなど一部を別の場所へ分けると、承認コミット（`server/src/git/gitRepo.ts` の `COMMITTED_PATHSPECS`）と版履歴が `dataRoot` 直下の固定名（`templates` / `filled` / `css` / `sync`）を前提にしているため、本文がコミットされなくなる。

手順（サーバを動かすアカウントで実行する）:

1. **`DATA_ROOT` を設定する**: `setx DATA_ROOT "\\fileserver\share\editor-data"`。ユーザー環境変数に入る。サービスやタスクスケジューラで別アカウントとして動かす場合は、そのアカウントに設定するかシステム環境変数にする。
2. **git の safe.directory に登録する**: `git config --global --add safe.directory "%(prefix)///fileserver/share/editor-data"`。共有フォルダは所有者が実行アカウントと一致しないことが多く、未登録だと git が `detected dubious ownership` で全コマンドを拒否し、承認コミットが失敗する。UNC は `%(prefix)/` を前置してスラッシュ区切りで書く。
3. **フォルダと git リポジトリを作る**: `editor\scripts\init-data-repo.bat`（引数なし）。`-DataRoot` 引数 → このウィンドウの `DATA_ROOT` → ユーザー環境変数 `DATA_ROOT` → appconfig の `paths.dataRoot`（環境変数 `APP_CONFIG` の指すファイル、無ければ `editor\appconfig.json`。editor のフォルダの中を指す値は使わない）→ 既定の順で作成先を決める（2 本のパッチと同じ順）。ユーザー環境変数まで見るので、`setx` 直後の同じウィンドウでも共有を向く。`dataRoot:` で始まる行（`dataRoot: …（読んだ元）`）で作成先を確かめる。何度実行してもよい（履歴があれば git には触らず、足りないフォルダだけを作る）。`.git` はあるが履歴（最初のコミット）が無い場合は、確定領域（`templates`・`filled`・`css`（`css\fonts` を除く）・`sync`・`.gitignore`・`.gitattributes`）だけで初回コミットを作る。`assets`・`js`・`images`・`notes` などは記録しない。git は環境変数 `GIT_BIN` があればそれを使う。
4. **（任意）git のタイムアウトを延ばす**: `setx GIT_TIMEOUT_MS 120000`（既定 30 秒）。共有上の git が遅い場合だけ設定する。
5. **起動する**: 新しいコマンドプロンプトから `start.bat` を起動する（`setx` は開いているウィンドウへ反映されない）。起動ログに `dataRoot はネットワークドライブ上です` と出れば共有を読めている。

`init-data-repo` が作る構成:

```
<dataRoot>\
  .git\  .gitignore  .gitattributes
  templates\  filled\  css\  sync\        git で記録する（承認ごとに 1 コミット）
  drafts\  pending\  reviews\  notes\    作業用。.gitignore 済み
  css\fonts\                             全ファンド共通のフォント。中身は手で置く（git 管理外）
  js\                                    全ファンド共通のテンプレ JS。中身は手で置く
  images\                                ファンド別画像。別ツールが置く（git 管理外。命名 <fund>_<名前>.<拡張子>）
```

> [!WARN] 既存の `editor-data` を移す場合は、先に `.git` ごと共有へコピーしてから `init-data-repo` を実行する（足りないフォルダだけが作られる）。

> [!WARN] `DATA_ROOT` はユーザー単位で効くため、同じユーザーで動かす editor はすべて共有を向く。検証用に別フォルダの editor を動かすときは、起動ラッパで `set DATA_ROOT=<検証用パス>` と上書きする。上書きしないと、検証中の承認が本番のテンプレートを書き換える。

運用の条件:

- 共有へ書き込む editor サーバは **1 台だけ**とする（プロセス間のロックが無い）。
- `LOG_DIR` と `TMP_DIR` はローカルディスクのままにする。共有上だと監査ログの欠落や PDF ビルドの遅延を招き、起動時に警告が出る。
- 他の端末が TortoiseGit やエクスプローラーで開いている間は、保存やコミットが待たされることがある（リトライ実装済み）。
- アクセス権は、サーバの実行アカウントに `dataRoot` 全体の変更権限、`filled/` へ HTML を置く別ツールのアカウントには `filled/` の変更権限、履歴を見るだけの人には読み取り権限を与える。`templates/` / `css/` / `filled/` を人が直接書き換えると承認を経ない変更になるため、修正は Editor の申請・承認から行う。

フォントの書き方:

- ファンド CSS から参照するときは `@font-face { src: url(fonts/x.woff2) }` と書く。CSS 自身から見た相対パスで、`fonts/` は小文字にする。
- HTML の `<style>` から参照するときは `css/fonts/x.woff2` と書く。HTML の `<style>` と `style` 属性は付け替えないので、配信パスのまま書く。

旧構成（`assets\fonts` / `assets\js`）からの移行は、3.3 節の手順 2（フォント移設パッチ）で行う。詳細と元に戻し方は `editor/patches/2026-10-fonts-to-css/README.md` を見る。

ファンド別画像の置き方:

- 置き場は `images\` の直下だけ。サブフォルダは作らない。拡張子は `.svg` `.png` `.jpg` `.jpeg`。
- ファイル名は `<fund>_<画像名>.<拡張子>`（例 `510037_logo.svg`）。名前の規則はエディタが検査しない約束で、守らないと他ファンドの画像も名前で参照できてしまう。
- 画像はエディタの外（値入り HTML を置く別ツールなど）が置く。エディタは読んで表示するだけで、アップロード・差し替え・削除はできない。
- 外部ツールへの約束: 書き込みは一時名で書いてから改名する（書きかけを読ませないため）。値入り HTML の参照は確定したパス（`images/510037_logo.svg`）で書き、`{{ fund.code }}` を残さない（残すと PDF・プレビュー・編集画面のどれにも出ず、編集画面に警告が出る）。SVG には `width` と `height` を書く（無いと 300×150 で表示される）。
- SVG は Illustrator の「書き出し（SVG 1.1）」または Inkscape の「プレーン SVG」で保存する。「Illustrator の編集機能を保持」で保存した SVG はサーバの検査で落ち、どの経路でも表示されない。落ちた SVG はサーバログに警告（ファイル名と違反の内容）が出る。

画像の書き方:

- テンプレ（作成タブ）: `<img src="images/{{ fund.code }}_logo.svg">`。`{{ fund.code }}` はテンプレのファンドコードに置き換わる。
- 値入り HTML（編集タブ）: `<img src="images/510037_logo.svg">`（確定したパス）。
- ファンド CSS: `background: url(../images/510037_logo.svg)`。CSS 自身（`css\`）から見た相対パスで書く。`url(images/…)` と書くと `css/images/…` になって表示されない。CSS の背景画像は PDF と画面内プレビューにだけ出て、編集画面には出ない。
- `style` 属性に書いた背景画像（`style="background:url(images/…)"`）は PDF には出るが画面内プレビューには出ない。背景画像はファンド CSS か `<style>` に書く。
- 画像を差し替えたあと、画面内プレビューへの反映はブラウザの再読み込みが必要（取得した画像はページを開いている間だけ覚えている）。

既存環境への画像の置き場の追加は、3.3 節の手順 3（画像の置き場パッチ）で行う。詳細と元に戻し方は `editor/patches/2026-10-fund-images/README.md` を見る。

## 3.2 テンプレート生成器を置く

作成タブの「新規作成」は、既存のテンプレート生成器（Python のスクリプト）を `python <スクリプト> <属性の JSON>` として起動する。`python` は PATH から探し、版は指定しない（3.13 かどうかは起動時の確認が知らせる）。生成器は editor のリポジトリには含まれず、社内の別サーバ・共有フォルダにある。editor は `python.script`（`PY_GENERATE_SCRIPT`）でそのパスを指す。既定のスクリプトはテスト用の偽物なので、本番では必ず設定する。

置き方:

- 生成器を置くフォルダは、editor サーバの実行アカウントから**読み取り専用**にする。書き込めるのは生成器の保守者だけにする。生成器が出した HTML の JS は承認後は変えられない基準になるので、生成器を書き換えられる人は、サーバの実行アカウントでコードを実行できるのと同じ重みを持つ。
- `dataRoot` の配下には置かない。データの git リポジトリに実行コードが入り、data リポジトリを書ける人が任意のコードを実行できるようになる。
- 生成器の子プロセスへ渡す環境変数は `PATH` `SYSTEMROOT` `TEMP` `TMP` `PATHEXT` `COMSPEC` と、`PYTHONUTF8` `PYTHONIOENCODING` `TEMPLATES_DIR`（元テンプレの読み先。サーバの `paths.templatesDir`）と `PENDING_DIR`（生成物の書き先。サーバの `paths.pendingDir`）だけ。生成器が他の環境変数（秘密値を含む）を読む前提にはしない。生成器はサーバの実行アカウントで動くので、`pending\` への書き込み権限を足す作業は無い。

生成器への入出力の約束: 属性の JSON は `companyCode`・`fundCode`・`editionType` と、シリーズから作成のときだけ `sourceFundCode`、償還のときだけ `isRedemption`。テンプレートは基準日を持たないので `baseDate` は渡さない。コピー元は `TEMPLATES_DIR` の `<会社コード>_<sourceFundCode>_<版種>.html`（基準日なし）で、生成器はこれを読む。生成器は結果を環境変数 `PENDING_DIR`（サーバの `paths.pendingDir`）の `<会社コード>_<ファンドコード>_<版種>.html` へ書く。書きかけを残さないよう、同じフォルダの一時ファイル（拡張子 `.html` 以外）に書いてから名前を変え、失敗したときは前のファイルに触れない。標準出力の HTML は使われない。editor は終了コード 0 でもこのファイルが書かれていなければ生成の失敗として扱う。本番の生成器はこの約束に合わせて改修してから、この版の editor を動かす。

Python 3.13 を PATH に通す（本番機・開発機とも、運用者が手で設定する）:

1. Python 3.13 を入れる。インストーラで「Add python.exe to PATH」を選ぶと、ユーザー環境変数 PATH の先頭に `…\Python313\` と `…\Python313\Scripts\` が入る。
2. 手で設定するときは、スタートメニューで「環境変数」と検索して「環境変数を編集」を開き、ユーザー環境変数 `Path` に上の 2 つを足して、`%LOCALAPPDATA%\Microsoft\WindowsApps` より**上**へ移す。WindowsApps の `python.exe` は Microsoft Store の偽物で、先に当たると終了コード 9009 で起動できない。「設定 → アプリ → アプリ実行エイリアス」で `python.exe` / `python3.exe` をオフにしてもよい。
3. `setx` で PATH を設定しない。1024 文字で切れ、既存の PATH の後半が失われる。
4. Windows のプロセスの PATH は「システム環境変数 `Path` の後にユーザー環境変数 `Path`」の順で探す。システムの `Path` に別の版の Python があると、ユーザーの `Path` の先頭に置いても負ける。その場合はシステムの `Path` からその行を外す（管理者が行う）か、`PYTHON_BIN` に Python 3.13 の `python.exe` の絶対パスを設定する。起動時の確認が版違いとして警告するので、それで気づける。
5. 設定したら**新しいコマンドプロンプト**で `where python`（1 件目が Python 3.13 の `python.exe`）と `python --version`（`Python 3.13.x`）を確かめる。起動中のサーバには反映されないので、サーバも新しいコマンドプロンプトから起動し直す。
6. サーバをサービスや別のアカウントで動かす場合は、そのアカウントの PATH が使われる。そのアカウントで同じ設定をする。

設定を誤ったときは、サーバの起動ログ（下の表）と offline の setup（`offline\setup-offline.bat`）の警告が知らせる。

指紋（SHA256）の設定:

1. 生成器のスクリプトの指紋を取る: `certutil -hashfile \\fileserver\share\generator\generate_template.py SHA256`。2 行目の 64 桁の 16 進が指紋。
2. 環境変数 `PY_GENERATE_SCRIPT_SHA256`（または appconfig の `python.scriptSha256`）に設定し、editor を起動し直す。64 桁の 16 進でなければ起動を中止する。
3. 生成器を更新したら、指紋も取り直して設定し直す。設定し直すまで、生成は拒否される。利用者には「テンプレート生成器の指紋が設定と一致しないため、生成を中止しました。管理者に連絡してください」と表示され、サーバログには `[generate] 生成器の指紋が設定と一致しません` で始まるエラーが、監査ログには `template.generate` の失敗が残る。

照合できるのは入口のスクリプト 1 本だけで、そこから読み込まれるモジュールは対象外。モジュールの改ざんは、上の読み取り専用の運用で防ぐ。

起動ログの警告の意味（左の列は、各ログ行の先頭部分の引用。行の後ろには括弧書きで起動コマンドやスクリプトのパスが続く）:

| 起動ログ（…で始まる行） | 意味と対応 |
|---|---|
| `[generate] 生成器の Python: 3.13(python)` | 正常 |
| `[generate] 生成器の Python を起動できません` | PATH に `python` が無い、または Microsoft Store の偽物（WindowsApps。終了コード 9009）に当たっている。上の「Python 3.13 を PATH に通す」に従い、新しいコマンドプロンプトから起動し直す |
| `[generate] 生成器の Python が 3.12 です` | PATH で先に見つかる `python` が 3.13 でない（システムの `Path` にある別の版など）。PATH を直すか、3.13 の `python.exe` の絶対パスを `PYTHON_BIN` に設定する。appconfig に `python.args` が残っていれば外す（`python.exe` に余計な引数が付いて失敗するため） |
| `[generate] 生成器の指紋が未設定です` | 指紋を照合していない。共有フォルダ上の生成器を使うなら、上の手順で設定する |
| `[generate] 生成器が偽物(テスト用)のままです` | `PY_GENERATE_SCRIPT` / `python.script` が既定の `fake_generate_template.py` のまま。本番では既存の生成器を指す。設定し忘れると、本物ではない HTML が生成される |
| `[generate] 生成器のスクリプトを読めず指紋を照合できません` | 起動時ではなく、生成のたびに出るエラー（この表の他の行と違い、起動ログには出ない）。指紋を設定しているのにスクリプトを読めない（パス違い・共有フォルダへの権限不足）。生成は拒否される。`python.script` のパスと editor を動かすアカウントの読み取り権限を確かめる |

本物の生成器が使う Python パッケージは、Python 3.13 の本体（site-packages）へ入れる（`pip install --user` では入れない）。生成器は許可した最小限の環境変数だけで起動するため、利用者ごとの領域に入れたパッケージは見つからない。

どの警告でも editor は起動する（生成を使わない運用を止めないため）。生成の同時実行は `GENERATE_MAX_CONCURRENCY`（既定 2）、待ち行列は `GENERATE_MAX_QUEUE`（既定 8）で、超えた要求は「テンプレート生成の順番待ちが混み合っています」で返る。

## 3.3 構築済み環境を新版へ上げる

フォントの置き場の移設（`css\fonts`・`js`）と画像の置き場（`images`）より前に構築した環境は、次の順で上げる。新版のサーバは旧構成のままでも起動を止めない。**手順 2 を飛ばすと、フォントと JS が欠けた PDF が成功扱いで出る**（起動ログに `[layout]` の警告は出る）。

> [!WARN] 手順 2 のフォント移設パッチは必須。飛ばしても editor は起動し、PDF も成功扱いで出るので、フォントと JS が欠けていることに気づきにくい。

1. editor サーバを止め、新版を配置する。2 本のパッチは editor サーバが動いていると中止する（既定のポート 24680 で確かめる。変えているときは `-Port <番号>` で渡す）。
   - あわせて、作成タブが読む `Rep1` の sproc を入れる（4.1 節）。`server\db\sproc\template.sql` と `series.sql` の仮のテーブル名・列名を実際の名前に合わせてから、`sqlcmd -S <host\instance> -d usrap -E -b -f 65001 -i server\db\sproc\template.sql`（`series.sql` も同じ）で流す。**流さないと作成タブの会社・ファンドが出ない。**
2. **（必須）フォント移設パッチを流す。** `editor\patches\2026-10-fonts-to-css\migrate.bat` を引数なしで実行し（確認モード。何も変えない）、表示を確かめてから `migrate.bat -Apply` で実行する。次がまとめて動く。
   - `assets\fonts` → `css\fonts`、`assets\js` → `js` のコピーと SHA256 の照合。照合の後、旧 `assets` は中身にかかわらず `assets.migrated-<日付>` へ改名して残す（フォントと js 以外のものは移さずに報告する）。
   - CSS の `url(../fonts/…)` → `url(fonts/…)` の書き換え（`css\*.css` と、承認前の作業コピー `drafts\*.css`・`pending\*.css`・`reviews\<id>\body.css`）。作業コピーは git 管理外なので、書き換える前に `<dataRoot>\.fonts-to-css-backup-<日付>\` へ退避する。
   - `.gitignore` への `/css/fonts/` の追記。
   - 追跡されているフォント・画像・js（`css/fonts`・`images`・`js`・`assets`）の追跡の解除（ファイルは残す）。
   - appconfig の片付け。editor のフォルダの外を指す `paths.assetsDir` は `paths.jsDir`（`<dataRoot>\js`）へ置き換える。editor のフォルダの中を指す置き場の設定（旧例の `data/templates` など）、旧い仮の生成器と偽の生成器を指す `python.script` は外す。`python.bin` / `python.args` は、既定と同じ組（`python` だけ）と元から起動できない組（`python -3.13`）、py ランチャの組（`py -3.13`。PATH 上の python へ移す）を外す。それ以外の `python.bin` / `python.args` は触らずに報告する。1 か所でも変えるときは、元を `appconfig.json.bak-<日付>`（同じ日の 2 回目以降は `-2`・`-3` … を付けた別名）に残す。
   - 確定領域の変更と追跡の解除を、`system` 名義の 1 コミット（件名の末尾に `[fonts-to-css]`）にまとめる。

   環境変数 `ASSETS_DIR` を設定していた場合は手で外す（新版は読まない。パッチは環境変数を変えない）。js の置き場を変えていたなら `JS_DIR` へ置き換える。報告に HTML の `fonts/` 参照や旧い形式のデータが出たら、手で直す。
3. 画像の置き場パッチを流す。`editor\patches\2026-10-fund-images\apply.bat`（確認モード）→ `apply.bat -Apply`。`.gitignore` に `/images/` を足し、`images` を作り、追跡されている画像・フォント・js の追跡を外して、`system` 名義の 1 コミット（件名の末尾に `[fund-images]`）にする。既に置かれた画像は点検して報告するだけで、動かしも消しもしない。`<dataRoot>\assets` が残っていると中止するので、必ず手順 2 の後に流す。
4. `editor\scripts\init-data-repo.bat` を流す（足りない置き場のフォルダだけを作る。履歴があれば git には触らない）。2 本のパッチの**後**に流す。`init-data-repo` は指した場所に `templates` と `css` を必ず作るので、先に流すと、dataRoot を取り違えていてもパッチの取り違えの検査（下記）が効かなくなる。`dataRoot:` で始まる行（`dataRoot: …（読んだ元）`）の場所が、パッチの `dataRoot :` で始まる行の場所と同じであることを確かめる（appconfig の `paths.dataRoot` が editor のフォルダの中を指して使わなかったときは、その案内がこの行より先に出る）。パッチを `-DataRoot` 付きで流した場合は、`init-data-repo.bat` にも同じ `-DataRoot` を付ける（付けないと、appconfig や既定の場所に別のリポジトリを作る）。
5. Python 3.13 が PATH で通っていることを確かめる（3.2 節）。Python 3.13 のフォルダと `Scripts` をユーザー環境変数 `Path` の、`%LOCALAPPDATA%\Microsoft\WindowsApps` より上に置く。システム環境変数 `Path` に別の版の Python があると、ユーザーの `Path` より先に探されて負ける。**新しいコマンドプロンプト**で `where python`（1 件目が Python 3.13 の `python.exe`）と `python --version`（`Python 3.13.x`）を確かめる。サーバをサービスや別のアカウントで動かす場合は、そのアカウントで確かめる。続けて、本番の生成器の場所を `PY_GENERATE_SCRIPT`、指紋を `PY_GENERATE_SCRIPT_SHA256` に設定する（3.2 節）。
6. 新しいコマンドプロンプトから起動し、起動ログに `[generate]`（Python を起動できない・版が 3.13 でない・指紋が未設定・偽物のまま）と `[layout]`（旧構成の残り）の警告が出ていないことを確かめる。フォントを使うテンプレートで PDF を出し、フォントと JS が効いていることを確かめる。

dataRoot を手で作り直した場合も、同じ手順で流す。2 本のパッチは結果を点検し、パッチが作るのと同じ形なら取り込んで直す。

- 未コミットの変更（`templates`・`filled`・`css`（`css\fonts` を除く）・`sync`・`.gitignore`・`.gitattributes`）は、パッチが作るのと同じ形なら取り込んで同じコミットに含める。同じ形とは、`css` 直下の CSS の `../fonts/` → `fonts/` の書き換えだけ、`.gitignore` への必須行（`/drafts/` `/reviews/` `/pending/` `/notes/` `/css/fonts/` `/images/` `*.tmp-*`）の追記だけ、`.gitattributes` を `* text eol=lf` にしただけ（旧い `* text=lf` は落とし、他の行は残す）、中身の無いフォルダの作成。BOM と改行コード（CRLF / LF）の違いは除いて比べる。
- それ以外の変更と、点検範囲の外でステージ済みの変更が 1 件でもあると、一覧を出して何も変えずに中止する（確認モードでも）。案内は 2 通りに分かれる。前回のパッチや rollback が途中で止まった形跡（`.git\index.lock`・`REVERT_HEAD`・`MERGE_HEAD`・`CHERRY_PICK_HEAD`）があれば `前回のパッチ(または rollback)が途中で止まった形跡があります`、無ければ `手作業の変更が残っています` で始まる。ただしフォント移設パッチで、移行コミットが無いのに `assets.migrated-*` があるときは、途中で止まったとは決めつけず、`前回のパッチの跡` で始めて「途中で止まったか、その後に手作業で変更したかのどちらか」と案内する。書き換えも追記も要らない構成では、正常に終わった `-Apply` も改名だけでコミットを作らないため。手作業の変更の場合は、残すならコミットする。要らなければ、ステージ済みのものを `git restore --staged -- <ファイル>` でステージから外し、変更したファイルは `git checkout -- <ファイル>` で戻し、新しく足したファイルは消してから流し直す。新しく足したファイルを `git checkout --` に渡すと、git の知らないファイルとして全体が失敗する。
- 追跡されているフォント・画像・js は、追跡だけを外す（ファイルは残す）。
- `.git` がまったく無い dataRoot と、`git init` だけで履歴の無い data リポジトリは、2 本のパッチとも終了コード 1 で中止し、`editor\scripts\init-data-repo.bat -DataRoot "<dataRoot>"` を案内する。この場合に限り `init-data-repo.bat` を先に流して初回コミット（確定領域だけを記録）を作り、それから手順 2 に戻る。
- `<dataRoot>\templates` も `<dataRoot>\css` も無いと、dataRoot の取り違えとして警告し、何も変えずに終了コード 2 で終わる。`-DataRoot <場所>` で正しい場所を指して流し直す。
- 配信されない場所のフォント（`<dataRoot>\fonts`・`css` 直下のフォント・`assets.migrated-*` 以外の `assets*`）と、新版が読まない旧い形式のデータ（配列でないメモ・`held` の申請・`filled` が無いこと）は、フォント移設パッチが報告だけする。旧い形式のデータは手で直す（メモは投稿の配列へ、`held` の申請は `pending` へ。`filled` は手順 4 で作られる）。

2 本のパッチの終了コードは、完了（確認モードを含む）が 0、中止（サーバの稼働・`.git` や履歴が無い・未コミットの変更・競合など）が 1、dataRoot の取り違えが 2。

元に戻すときは、editor サーバを止め、2 本のパッチの `rollback.bat`（確認）→ `rollback.bat -Apply` を、画像の置き場 → フォント移設の順に流してから、旧版の editor を配置する。逆の順だと `.gitignore` の revert が競合する。フォント移設の `rollback.bat` は、戻す日付の候補（`assets.migrated-<日付>`・`appconfig.json.bak-<日付>`・`.fonts-to-css-backup-<日付>`）が複数あれば `-Date <yyyyMMdd>` を求める。rollback が `【残す】` や `退避に残しました` を報告したら、戻した版と見比べて手で片付ける（改行コードの違いだけのこともある）。

rollback の revert は移行コミットをまるごと戻す。2 本のパッチが `-Apply` で取り込んだ手作業の未コミットの変更（上の「同じ形」: CSS の `../fonts/` → `fonts/` の書き換え、`.gitignore` へ足した必須行、`* text eol=lf` にした `.gitattributes`）も同じコミットに入っているので、それらも戻る。戻った先は、手作業を始める前のコミット済みの状態になる。手作業の分を残したいときは、rollback の後にやり直してコミットする。

# 4. SQL Server セットアップ（rest モード）

ターゲットは **SQL Server 2012**、DB `usrap`、既存スキーマ `ug01`、テーブル接頭辞 `Rep1_運報自動化_Editor_`。DB アクセスは 8 本のゲートウェイ sproc（第 1 引数 `@操作` で分岐）を通す（設計書 10.1 節参照）。

DDL/sproc/seed は `server/db/` に置く。

```
ddl/    01_テーブル.sql 02_索引.sql 03_制約.sql
sproc/  audit / noteMaster / part / sample / series / session / template / user の 8 本（DROP + CREATE）
dev/    Rep1_検証用.sql（検証用の Rep1）/ 台帳_削除.sql（旧テンプレート台帳の DROP）。apply.ps1 の対象外
seed/   管理ユーザー.sql / パーツカタログ.sql / サンプルデータ.sql
```

> [!WARN] 全 SQL ファイルは **UTF-8 BOM 保存**（日本語識別子 + sqlcmd の cp932 対策）。SQL Server 2012 互換のため `CREATE OR ALTER` / `OPENJSON` / `FOR JSON` / `STRING_AGG` は不使用。

適用手順:

```
# 1) seed SQL を生成（管理ユーザーのパスワードハッシュ + seed）
corepack pnpm --filter server exec tsx scripts/hash-password.ts admin "<パスワード>" 管理者 admin
corepack pnpm --filter server exec tsx scripts/gen-seed.ts

# 2) 適用（Windows 統合認証）
powershell -ExecutionPolicy Bypass -File server\db\apply.ps1 -Server <host\instance>
```

`apply.ps1` が ddl → sproc → seed の順に適用する。

## 4.1 Rep1 のファンド属性を読む sproc

作成タブの委託会社・ファンド・シリーズは、同じサーバの `Rep1` にあるファンド属性を、usrap の sproc（`template` の `委託会社一覧` / `ファンド一覧`、`series` の `一覧`）から 3 部名で読む。テーブル名と列名は仮で、sproc の中だけに書いてある。

| sproc が返す列（変えない） | 仮の読み元 |
|---|---|
| `委託会社コード` / `委託会社名` / `委託会社略称` | `Rep1.dbo.Rep1_投委託会社` |
| `ファンドコード` / `ファンド名` | `Rep1.dbo.Rep1_投信ファンド属性` |
| `ファンドコード` / `シリーズコード` | `Rep1.dbo.Rep1_投信ファンド属性` |

1. 実際のテーブル名・列名に合わせて、`template.sql` と `series.sql` の `FROM` と各列の元の名前を直す（`AS` の右の列名は変えない）。`委託会社略称` は、テンプレートのファイル名に使う会社コード（`AM01` / `smtam` など）に当たる列にする。
2. `template.sql` と `series.sql` を流す（上の `apply.ps1` か、1 本ずつ `sqlcmd … -i server\db\sproc\<ファイル>`）。
3. 確かめる: `sqlcmd -S <host\instance> -d usrap -E -f 65001 -Q "EXEC [ug01].[Rep1_運報自動化_Editor_usp_テンプレート] @操作=N'委託会社一覧'"` で、会社と略称が返ること。

作成タブで「データベース処理に失敗しました」と出るときは、次を疑う。

- `series.sql` を流し忘れていないか（会社・ファンドは出るのに、3 つ選ぶと失敗する）。
- editor を動かすアカウントが `Rep1` の 2 テーブルを読めるか（DB をまたぐ参照は所有権の連鎖が既定で効かないため、`Rep1` 側にそのアカウントの SELECT 権限が要る）。

旧版で作ったテンプレート台帳（`ug01.Rep1_運報自動化_Editor_テンプレート台帳`）は editor が読まなくなった。不要なら `server\db\dev\台帳_削除.sql` で消す（任意）。

| LAN 公開（本番 + REST + HTTPS） | `start.bat rest lan`（事前に `scripts\setup-lan-https.bat` と `scripts\setup-lan-firewall.bat` を各 1 回実行。詳細は editor/README.md「LAN 公開」節） |

rest モードは `VITE_API_MODE=rest` / `AUTH_REQUIRED=true` / `AUDIT_DB=true` を有効化し、Repository を REST 実装に差し替えて SQL Server に接続する。

> [!NOTE] rest モードに必要な msnodesqlv8 のネイティブバイナリは、オフラインバンドルの `native-prebuilds/` に同梱済み（版は `native-prebuilds/manifest.txt`）。`offline/setup-offline.bat` が `pnpm install --offline` の後に node_modules へ展開する。Node は ABI が一致する 24.x が必須（不一致は setup の require 疎通確認が警告する）。

# 6. オフライン検証チェックリスト

1. **調達**: バンドル tar.gz（`.pnpm-store/`・`pnpm.tgz`・`ms-playwright/` 同梱）が生成される。
2. **遮断**: ネット遮断で `offline/setup-offline.bat` の展開〜`pnpm build` が完走、ネイティブ取得が走らない。
3. **起動**: `GET /api/health` → `{ok:true}`、ブラウザで SPA 表示、DevTools で外部通信なし。
4. **PDF（最重要）**: `POST /api/build` で PDF 生成成功、Edge 自動検出が機能、MathJax（数式描画）を読み込めなくても停止・失敗しない。
5. **生成/保存**: `POST /api/generate`・`PUT /api/templates/:id/draft`・`POST /api/review-requests`（確定保存の申請）が成功。
6. **エディタ UI**: GrapesJS のアイコン/スタイルに欠けがない。
7. **回帰**: `pnpm typecheck`・`pnpm check:ci` が通る（typecheck は `@editor/shared` 先行ビルドが前提）。
8. **rest モードのみ**: setup ログに「msnodesqlv8 ネイティブ .node を配置（require OK）」が出る（= `sqlserverv8.node` 配置済み。DB 接続自体は 4 章の適用後に `POST /api/auth/login` で確認）。

# 7. 監査ログ

- 監査ログは `logs/audit.log`（`logging.level` / `logging.pretty` で制御）。rest モードでは `AUDIT_DB=true` で監査ログ sproc にも記録する。
- ログレベル既定は `info`（`LOG_LEVEL` で上書き可）。本番は `NODE_ENV=production` で Pretty 無効（`LOG_PRETTY` で上書き可）。

# 8. SQL エラーと HTTP の対応

`server/src/db/sproc.ts` が SQL エラーを HTTP へマップする。運用時の切り分けに使う。

| SQL エラー | 種別 | HTTP |
|---|---|---|
| `THROW 50404` | not_found | 404 |
| `THROW 50409` / 一意制約 2627・2601 | conflict | 409 |
| `THROW 50000` / `THROW 50400`（必須パラメタ不足等） | validation | 400 |
| その他 | unexpected | 500 |
