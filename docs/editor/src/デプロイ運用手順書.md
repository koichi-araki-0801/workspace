本書は Editor を運用端末に構築し、運用するための手順を、情報システム担当向けにまとめる。内部構造は別冊「Editor 詳細設計書」を参照。rest モード（REST + SQL Server。既定）と local モード（fixtures + localStorage。開発用）の両方を扱う。

# 1. 構成方針

- **PDF 生成はサーバ側に集約**（運用端末 1 台）。ブラウザは社内 Windows の Microsoft Edge を使う（Chromium 同梱なし）。
- **依存はオフライン調達**: pnpm オフラインストア（`.pnpm-store/`）を tar.gz で持ち込み、運用端末で復元する。
- フォントは @fontsource でローカル同梱（Google Fonts CDN 非依存）。
- 前提: パッケージマネージャ `pnpm@11.18.0+`、Node `>=24`。

> [!WARN] 調達端末と運用端末は **Windows x64・Node 24 で一致**させること（msnodesqlv8 等のネイティブバイナリが必要）。

# 2. オフライン調達・展開

1. **調達**: 配布担当の端末で重量物バンドルを生成し GitHub Releases へ置く（git 管理外の `local-only/offline-publish/`。依存を変えたら手動で実行する）。
2. **持ち込み・展開**: 運用端末の多くは `git clone` できない。ネットに出られる端末で `offline/fetch-offline-bundle.bat -Source` を実行し、Release から重量物バンドルとソース ZIP（`source.zip` / `.sha256`）を合わせて取得する。取得した 5 ファイル（`offline-deps-bundle.tar.gz` / `.sha256` / `bundle.key` / `source.zip` / `source.zip.sha256`）を運用端末へ持ち込み、初回は `source.zip` を新しいフォルダへ展開し、重量物 3 ファイルをその直下へ置いてから `offline/setup-offline.bat` を実行し、更新は新しい `source.zip` を直下に置いて同じ `offline/setup-offline.bat` を再実行する（setup が旧版の削除・展開・構築までを完走させる）。`git clone` できる端末では、リポジトリを clone したうえで `offline/fetch-offline-bundle.bat` → `offline/setup-offline.bat` の順に実行すればよい（source.zip の展開は不要）。いずれの経路も setup は取得を行わず、ネイティブバイナリの追加取得も走らないこと。
3. **検証**: 5 章のチェックリストを実施する。

## 3.1 data リポジトリをファイルサーバの共有へ置く

テンプレート実体（`dataRoot`）は、UNC パス（`\\fileserver\share\editor-data` など）の共有フォルダへ置ける。コードの変更は要らず、環境変数 `DATA_ROOT` を向けるだけで切り替わる。置くのは `dataRoot` **全体**とする。`filled/` だけなど一部を別の場所へ分けると、承認コミット（`server/src/git/gitRepo.ts` の `COMMITTED_PATHSPECS`）と版履歴が `dataRoot` 直下の固定名（`templates` / `filled` / `css` / `sync`）を前提にしているため、本文がコミットされなくなる。

手順（サーバを動かすアカウントで実行する）:

1. **`DATA_ROOT` を設定する**: `setx DATA_ROOT "\\fileserver\share\editor-data"`。ユーザー環境変数に入る。サービスやタスクスケジューラで別アカウントとして動かす場合は、そのアカウントに設定するかシステム環境変数にする。
2. **git の safe.directory に登録する**: `git config --global --add safe.directory "%(prefix)///fileserver/share/editor-data"`。共有フォルダは所有者が実行アカウントと一致しないことが多く、未登録だと git が `detected dubious ownership` で全コマンドを拒否し、承認コミットが失敗する。UNC は `%(prefix)/` を前置してスラッシュ区切りで書く。
3. **フォルダと git リポジトリを作る**: `editor\scripts\init-data-repo.bat`（引数なし）。`-DataRoot` 引数 → このウィンドウの `DATA_ROOT` → ユーザー環境変数 `DATA_ROOT` → 既定の順で作成先を決めるので、`setx` 直後の同じウィンドウでも共有を向く。1 行目の `dataRoot: …（読んだ元）` の表示で作成先を確かめる。何度実行してもよい。
4. **（任意）git のタイムアウトを延ばす**: `setx GIT_TIMEOUT_MS 120000`（既定 30 秒）。共有上の git が遅い場合だけ設定する。
5. **起動する**: 新しいコマンドプロンプトから `start.bat` を起動する（`setx` は開いているウィンドウへ反映されない）。起動ログに `dataRoot はネットワークドライブ上です` と出れば共有を読めている。

`init-data-repo` が作る構成:

```
<dataRoot>\
  .git\  .gitignore  .gitattributes
  templates\  filled\  css\  sync\        git で記録する（承認ごとに 1 コミット）
  drafts\  pending\  reviews\  notes\    作業用。.gitignore 済み
  css\fonts\                             全ファンド共通のフォント。中身は手で置く（git 管理外）
  js\                                    全ファンド共通のテンプレ JS。中身は手で置く
```

> [!WARN] リポジトリ内に `editor/data/` があると、その `templates` / `css`（サンプル）が共有へコピーされて初回コミットに入る。空の状態で始めるなら、実行前に `editor/data/` を退避する。既存の `editor-data` を移す場合は、先に `.git` ごと共有へコピーしてから `init-data-repo` を実行する（足りないフォルダだけが作られる）。

> [!WARN] `DATA_ROOT` はユーザー単位で効くため、同じユーザーで動かす editor はすべて共有を向く。検証用に別フォルダの editor を動かすときは、起動ラッパで `set DATA_ROOT=<検証用パス>` と上書きする。上書きしないと、検証中の承認が本番のテンプレートを書き換える。

運用の条件:

- 共有へ書き込む editor サーバは **1 台だけ**とする（プロセス間のロックが無い）。
- `LOG_DIR` と `TMP_DIR` はローカルディスクのままにする。共有上だと監査ログの欠落や PDF ビルドの遅延を招き、起動時に警告が出る。
- 他の端末が TortoiseGit やエクスプローラーで開いている間は、保存やコミットが待たされることがある（リトライ実装済み）。
- アクセス権は、サーバの実行アカウントに `dataRoot` 全体の変更権限、`filled/` へ HTML を置く別ツールのアカウントには `filled/` の変更権限、履歴を見るだけの人には読み取り権限を与える。`templates/` / `css/` / `filled/` を人が直接書き換えると承認を経ない変更になるため、修正は Editor の申請・承認から行う。

フォントの書き方:

- ファンド CSS から参照するときは `@font-face { src: url(fonts/x.woff2) }` と書く。CSS 自身から見た相対パスで、`fonts/` は小文字にする。
- HTML の `<style>` から参照するときは `css/fonts/x.woff2` と書く。HTML の `<style>` と `style` 属性は付け替えないので、配信パスのまま書く。

旧構成（`assets\fonts` / `assets\js`）からの移行:

1. editor サーバを止める。
2. 新版を配置する。
3. `editor\patches\2026-10-fonts-to-css\migrate.bat` を引数なしで実行し、確認モードで変更内容を見る（何も変えない）。
4. `migrate.bat -Apply` で実行する。フォントと js の移動、CSS 内のフォント参照の書き換え、`.gitignore` への `/css/fonts/` の追記、appconfig の `paths.assetsDir` から `paths.jsDir` への書き換えを行う。環境変数 `ASSETS_DIR` は変えないので、設定していたら `JS_DIR` へ置き換える。
5. editor を起動する。

元に戻すときは、サーバを止めて `rollback.bat`（確認）、`rollback.bat -Apply` の順に実行する。詳細は `editor/patches/2026-10-fonts-to-css/README.md` を見る。

# 4. SQL Server セットアップ（rest モード）

ターゲットは **SQL Server 2012**、DB `usrap`、既存スキーマ `ug01`、テーブル接頭辞 `Rep1_運報自動化_Editor_`。DB アクセスは 7 本のゲートウェイ sproc（第 1 引数 `@操作` で分岐）を通す（設計書 10.1 節参照）。

DDL/sproc/seed は `server/db/` に置く。

```
ddl/    01_テーブル.sql 02_索引.sql 03_制約.sql
sproc/  audit / noteMaster / part / sample / session / template / user の 7 本（DROP + CREATE）
seed/   管理ユーザー.sql / パーツカタログ.sql / サンプルデータ.sql
```

> [!WARN] 全 SQL ファイルは **UTF-8 BOM 保存**（日本語識別子 + sqlcmd の cp932 対策）。SQL Server 2012 互換のため `CREATE OR ALTER` / `OPENJSON` / `FOR JSON` / `STRING_AGG` は不使用。

適用手順:

```
# 1) seed SQL を生成（管理ユーザーのパスワードハッシュ + seed）
corepack pnpm --filter server exec tsx scripts/hash-password.ts admin "<パスワード>" 管理者 admin
corepack pnpm --filter server exec tsx scripts/gen-seed.ts

# 2) 適用（Windows 統合認証）
powershell -ExecutionPolicy Bypass -File server\db\apply.ps1 -Server <host\instance>
```

`apply.ps1` が ddl → sproc → seed の順に適用する。

# 5. 起動（モード別）

`start.bat` のモードで起動する。

| 用途 | コマンド |
|---|---|
| 開発（Fastify:24680 + Vite:24681） | `pnpm dev` または `start.bat dev` |
| 本番（ビルド後 :24680 単体） | `pnpm build` 後 `pnpm --filter server run start`、または `start.bat prod` |
| rest モード（開発） | `start.bat dev rest` |
| rest モード（本番） | `start.bat prod rest` |
| LAN 公開（本番 + REST + HTTPS） | `start.bat rest lan`（事前に `scripts\setup-lan-https.bat` と `scripts\setup-lan-firewall.bat` を各 1 回実行。詳細は editor/README.md「LAN 公開」節） |

rest モードは `VITE_API_MODE=rest` / `AUTH_REQUIRED=true` / `AUDIT_DB=true` を有効化し、Repository を REST 実装に差し替えて SQL Server に接続する。

> [!NOTE] rest モードに必要な msnodesqlv8 のネイティブバイナリは、オフラインバンドルの `native-prebuilds/` に同梱済み（版は `native-prebuilds/manifest.txt`）。`offline/setup-offline.bat` が `pnpm install --offline` の後に node_modules へ展開する。Node は ABI が一致する 24.x が必須（不一致は setup の require 疎通確認が警告する）。

# 6. オフライン検証チェックリスト

1. **調達**: バンドル tar.gz（`.pnpm-store/`・`pnpm.tgz`・`ms-playwright/` 同梱）が生成される。
2. **遮断**: ネット遮断で `offline/setup-offline.bat` の展開〜`pnpm build` が完走、ネイティブ取得が走らない。
3. **起動**: `GET /api/health` → `{ok:true}`、ブラウザで SPA 表示、DevTools で外部通信なし。
4. **PDF（最重要）**: `POST /api/build` で PDF 生成成功、Edge 自動検出が機能、MathJax（数式描画）を読み込めなくても停止・失敗しない。
5. **生成/保存**: `POST /api/generate`・`PUT /api/templates/:id/draft`・`POST /api/review-requests`（確定保存の申請）が成功。
6. **エディタ UI**: GrapesJS のアイコン/スタイルに欠けがない。
7. **回帰**: `pnpm typecheck`・`pnpm check:ci` が通る（typecheck は `@editor/shared` 先行ビルドが前提）。
8. **rest モードのみ**: setup ログに「msnodesqlv8 ネイティブ .node を配置（require OK）」が出る（= `sqlserverv8.node` 配置済み。DB 接続自体は 4 章の適用後に `POST /api/auth/login` で確認）。

# 7. 監査ログ

- 監査ログは `logs/audit.log`（`logging.level` / `logging.pretty` で制御）。rest モードでは `AUDIT_DB=true` で監査ログ sproc にも記録する。
- ログレベル既定は `info`（`LOG_LEVEL` で上書き可）。本番は `NODE_ENV=production` で Pretty 無効（`LOG_PRETTY` で上書き可）。

# 8. SQL エラーと HTTP の対応

`server/src/db/sproc.ts` が SQL エラーを HTTP へマップする。運用時の切り分けに使う。

| SQL エラー | 種別 | HTTP |
|---|---|---|
| `THROW 50404` | not_found | 404 |
| `THROW 50409` / 一意制約 2627・2601 | conflict | 409 |
| `THROW 50000` / `THROW 50400`（必須パラメタ不足等） | validation | 400 |
| その他 | unexpected | 500 |
