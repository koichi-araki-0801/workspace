本書は Editor を運用端末に構築し、運用するための手順を、情報システム担当向けにまとめる。内部構造は別冊「Editor 詳細設計書」を参照。web のデータの取り出し口は rest モード（REST + SQL Server）の 1 系統だけである（開発用だった local モードは撤去した）。

# 1. 構成方針

- **PDF 生成はサーバ側に集約**（運用端末 1 台）。ブラウザは社内 Windows の Microsoft Edge を使う（Chromium 同梱なし）。
- **依存はオフライン調達**: pnpm オフラインストア（`.pnpm-store/`）を tar.gz で持ち込み、運用端末で復元する。
- フォントは @fontsource でローカル同梱（Google Fonts CDN 非依存）。
- 前提: パッケージマネージャ `pnpm@11.18.0+`、Node `>=24`。

> [!WARN] 調達端末と運用端末は **Windows x64・Node 24 で一致**させること（Node は engines の `>=24`。msnodesqlv8 のネイティブバイナリは Windows x64 用）。

# 2. オフライン調達・展開

1. **調達**: 配布担当の端末で重量物バンドルを生成し GitHub Releases へ置く（git 管理外の `local-only/offline-publish/`。依存を変えたら手動で実行する）。
2. **持ち込み・展開**: 運用端末の多くは `git clone` できない。ネットに出られる端末で `offline/fetch-offline-bundle.bat -Source` を実行し、Release から重量物バンドルとソース ZIP（`source.zip` / `.sha256`）を合わせて取得する。取得した 5 ファイル（`offline-deps-bundle.tar.gz` / `.sha256` / `bundle.key` / `source.zip` / `source.zip.sha256`）を運用端末へ持ち込み、初回は `source.zip` を新しいフォルダへ展開し、重量物 3 ファイルをその直下へ置いてから `offline/setup-offline.bat` を実行し、更新は新しい `source.zip` を直下に置いて同じ `offline/setup-offline.bat` を再実行する（setup が旧版の削除・展開・構築までを完走させる）。`git clone` できる端末では、リポジトリを clone したうえで `offline/fetch-offline-bundle.bat` → `offline/setup-offline.bat` の順に実行すればよい（source.zip の展開は不要）。いずれの経路も setup は取得を行わず、ネイティブバイナリの追加取得も走らないこと。
3. **検証**: 5 章のチェックリストを実施する。

PDF 出力は、1 人あたり実行中 1 件・待ち 1 件までに絞っている（設定は無い）。超えた要求には、画面に「前の PDF の出力が終わってから、もう一度出してください」と出る（API の応答は 503、`code: BUILD_BUSY_USER`）。PDF 生成のブラウザは、WebRTC がプロキシを通らない UDP を使わない設定で起動する。設定を付けられないとき（`@vivliostyle/cli` の版を上げて形が変わったときなど）は PDF 生成が失敗し、サーバのコンソール出力（常駐ワーカーの標準エラー）に `[browserLaunchGuard]` で始まる行が出る。`@vivliostyle/cli`・PDF 用ブラウザ（Edge）の版を上げたときは、開発機でリポジトリのルートから `set EDITOR_REAL_BROWSER_TEST=1` のあと `corepack pnpm exec vitest run --project server editor/server/test/browserLaunchGuard.realBrowser.test.ts` を流し、WebRTC が止まっていること（ICE 候補が 0 件）を確かめる。外部のホストへは通信しない。

`paths.assetsDir` は廃止した。appconfig に残っていると、不明なキーとして読み込みエラーになり起動しない（`paths.jsDir` へ置き換える）。環境変数 `ASSETS_DIR` は読まない（設定されていても何も起きないので、手で外す）。フォントは `paths.cssDir` の下の `fonts/` に、js は `paths.jsDir` に置く。

旧構成（`<dataRoot>\assets`、CSS の `url(../fonts/…)`）は読まない。残っていても起動は止まらず、警告も出ない。そのまま使うと、フォントと JS が欠けた PDF が成功扱いで出る。

## 3.1 data リポジトリをファイルサーバの共有へ置く

テンプレート実体（`dataRoot`）は、UNC パス（`\\fileserver\share\editor-data` など）の共有フォルダへ置ける。コードの変更は要らず、環境変数 `DATA_ROOT` を向けるだけで切り替わる。置くのは `dataRoot` **全体**とする。`filled/` だけなど一部を別の場所へ分けると、承認コミット（`server/src/git/gitRepo.ts` の `COMMITTED_PATHSPECS`）と版履歴が `dataRoot` 直下の固定名（`templates` / `filled` / `css` / `sync`）を前提にしているため、本文がコミットされなくなる。

手順（サーバを動かすアカウントで実行する）:

1. **`DATA_ROOT` を設定する**: `setx DATA_ROOT "\\fileserver\share\editor-data"`。ユーザー環境変数に入る。サービスやタスクスケジューラで別アカウントとして動かす場合は、そのアカウントに設定するかシステム環境変数にする。
2. **git の safe.directory に登録する**: `git config --global --add safe.directory "%(prefix)///fileserver/share/editor-data"`。共有フォルダは所有者が実行アカウントと一致しないことが多く、未登録だと git が `detected dubious ownership` で全コマンドを拒否し、承認コミットが失敗する。UNC は `%(prefix)/` を前置してスラッシュ区切りで書く。この登録は、他人が所有するリポジトリを開くときの git の検査を外すものである。登録する前に、手順 2-1 で `.git` の権限を絞る。
   1. **`.git` はサーバの実行アカウントと運用者のアカウントだけが書けるようにする**: `icacls "\\fileserver\share\editor-data\.git"` で権限を確かめ、実行アカウントと、単独で create_report.py を動かす運用者のアカウント（と管理者）以外に書き込み（`(M)` `(F)` `(W)`）が付いていれば外す。運用者には変更権限（`(M)`）を足す（単独の `--html-only` が `.git` へコミットを書くため。3.2.1 節）。履歴を見る人には読み取り（`(RX)`）だけを与える。editor の git はフック・fsmonitor・gpg・外部 diff を全呼び出しで切っているが、`.git` の中の設定（`.git\info\attributes` と filter の組み合わせなど）は切り切れない。`.git` に書ける人は、承認のたびにサーバの実行アカウントで任意のコマンドを動かせる。運用者のアカウントに書き込みを与えると、この仕掛けを置ける人がサーバの実行アカウントだけから運用者まで広がる。これは既知の前提として受け入れている（単独の create_report.py を動かす運用者はスクリプトを書き換えられる立場でもあり、権限が実質同じなため）。権限を絞れない共有では、`.git` を共有の外（サーバのローカルディスク）に置く（`GIT_DIR` を分ける構成）ことを検討する。
3. **フォルダと git リポジトリを作る**: `editor\scripts\init-data-repo.bat`（引数なし）。`-DataRoot` 引数 → このウィンドウの `DATA_ROOT` → ユーザー環境変数 `DATA_ROOT` → appconfig の `paths.dataRoot`（環境変数 `APP_CONFIG` の指すファイル、無ければ `editor\appconfig.json`。editor のフォルダの中を指す値は使わない）→ 既定の順で作成先を決める（2 本のパッチと同じ順）。ユーザー環境変数まで見るので、`setx` 直後の同じウィンドウでも共有を向く。`dataRoot:` で始まる行（`dataRoot: …（読んだ元）`）で作成先を確かめる。何度実行してもよい（履歴があれば git には触らず、足りないフォルダだけを作る）。`.git` はあるが履歴（最初のコミット）が無い場合は、確定領域（`templates`・`filled`・`css`（`css\fonts` を除く）・`sync`・`.gitignore`・`.gitattributes`）だけで初回コミットを作る。`assets`・`js`・`images`・`notes` などは記録しない。git は環境変数 `GIT_BIN` があればそれを使う。
4. **（任意）git のタイムアウトを延ばす**: `setx GIT_TIMEOUT_MS 120000`（既定 30 秒）。共有上の git が遅い場合だけ設定する。
5. **起動する**: 新しいコマンドプロンプトから `start.bat` を起動する（`setx` は開いているウィンドウへ反映されない）。起動ログに `dataRoot はネットワークドライブ上です` と出れば共有を読めている。

`init-data-repo` が作る構成:

```
<dataRoot>\
  .git\  .gitignore  .gitattributes
  templates\  filled\  css\  sync\        git で記録する（承認ごとに 1 コミット）
  drafts\  pending\  reviews\  notes\    作業用。.gitignore 済み
  css\fonts\                             全ファンド共通のフォント。中身は手で置く（git 管理外）
  js\                                    全ファンド共通のテンプレ JS。中身は手で置く
  images\                                ファンド別画像。別ツールが置く（git 管理外。命名 <fund>_<名前>.<拡張子>）
```

> [!WARN] 既存の `editor-data` を移す場合は、先に `.git` ごと共有へコピーしてから `init-data-repo` を実行する（足りないフォルダだけが作られる）。

> [!WARN] `DATA_ROOT` はユーザー単位で効くため、同じユーザーで動かす editor はすべて共有を向く。検証用に別フォルダの editor を動かすときは、起動ラッパで `set DATA_ROOT=<検証用パス>` と上書きする。上書きしないと、検証中の承認が本番のテンプレートを書き換える。

運用の条件:

- 共有へ書き込む editor サーバは **1 台だけ**とする（プロセス間のロックが無い）。
- `LOG_DIR` と `TMP_DIR` はローカルディスクのままにする。共有上だと監査ログの欠落や PDF ビルドの遅延を招き、起動時に警告が出る。
- `paths.tmpDir`（`TMP_DIR`。git の空のフック置き場 `git-empty-hooks` を含む）はサーバのローカルに置く。共有の上に置かない。共有の上に置くと、そこへ書ける人がフック置き場にファイルを置けてしまう（中身があれば承認の git は起動せずに失敗するが、承認が止まる）。
- 他の端末が TortoiseGit やエクスプローラーで開いている間は、保存やコミットが待たされることがある（リトライ実装済み）。
- アクセス権は、サーバの実行アカウントに `dataRoot` 全体の変更権限、`filled/` へ HTML を置く別ツールのアカウントには `filled/` の変更権限、履歴を見るだけの人には読み取り権限を与える。`.git` に書き込めるのはサーバの実行アカウントと運用者のアカウントだけにする（手順 2-1）。`templates/` / `css/` / `filled/` を人が直接書き換えると承認を経ない変更になるため、修正は Editor の申請・承認から行う。

CSS の置き方:

- テンプレの CSS は `css\<会社>_<ファンド>_<版種>.css`（例 `css\XXAM_910024_交付版.css`）。基準日違いの値入り HTML は同じ CSS を共有し、交付版と全体版は別の CSS になる。承認で CSS が変わると、同じテンプレの他の基準日にも効く。
- エディタは文書の ID から CSS の名前を決め、`<link href>` の値は見ない。値入り HTML の `<link>` は `../css/XXAM_910024_交付版.css` と書く。
- ファイル名の大文字小文字は区別せずに探す。綴りだけ違う同じ名前の CSS が 2 つあるとエラーになるので、1 つにまとめる。
- CSS ファイルが無いときは、スタイルを当てずに開き、編集画面とプレビューに「CSS <名前> が見つかりません。スタイルを当てずに表示しています」と出る。
- 交付版と全体版のどちらかの CSS を承認で直すと、変わった規則だけがもう一方の CSS へ写る。もう一方で同じ規則を版種に合わせて直してあるときは写さず、編集画面の同期のバナーに競合として出す。

フォントの書き方:

- テンプレの CSS から参照するときは `@font-face { src: url(fonts/x.woff2) }` と書く。CSS 自身から見た相対パスで、`fonts/` は小文字にする。
- HTML の `<style>` から参照するときは `../css/fonts/x.woff2` と書く。文書（`filled\` などのフォルダの中）から見た相対パスで書く。HTML の `<style>` と `style` 属性は付け替えない。

ファンド別画像の置き方:

- 置き場は `images\` の直下と、1 段下の会社フォルダ（例 `images\xxam\`）。2 段以上の下は配信されない。拡張子は `.svg` `.png` `.jpg` `.jpeg`。
- 会社フォルダ名はテンプレの会社コードと大文字小文字の違いだけを許す（`XXAM` のテンプレなら `xxam` も `XXAM` も可）。違う名前のフォルダの画像は、編集画面・プレビュー・PDF のどれにも出ず、編集画面とプレビューに警告が出る。
- 直下のファンド別画像のファイル名は `<fund>_<画像名>.<拡張子>`（例 `950037_logo.svg`）。名前の規則はエディタが検査しない約束で、守らないと他ファンドの画像も名前で参照できてしまう。会社フォルダの画像（例 `qr_code.svg`）は名前の約束を持たない。
- 名前の末尾が `.` や空白のもの、`:` を含むものは配信されない（Windows が別の名前として読み替えるため）。
- 画像はエディタの外（値入り HTML を置く別ツールなど）が置く。エディタは読んで表示するだけで、アップロード・差し替え・削除はできない。
- 外部ツールへの約束: 書き込みは一時名で書いてから改名する（書きかけを読ませないため）。値入り HTML の参照は文書から見た確定パス（`../images/950037_logo.svg`）で書き、`{{ fund.code }}` を残さない（残すと PDF・プレビュー・編集画面のどれにも出ず、警告が出る）。SVG には `width` と `height` を書く（無いと 300×150 で表示される）。
- SVG は Illustrator の「書き出し（SVG 1.1）」または Inkscape の「プレーン SVG」で保存する。「Illustrator の編集機能を保持」で保存した SVG はサーバの検査で落ち、どの経路でも表示されない。落ちた SVG はサーバログに警告（ファイル名と違反の内容）が出る。

画像の書き方:

- テンプレ（作成タブ）: `<img src="../images/{{ fund.code }}_logo.svg">`。`{{ fund.code }}` はテンプレのファンドコードに置き換わる。
- 値入り HTML（編集タブ）: `<img src="../images/950037_logo.svg">`（確定したパス）。会社共通の画像は `<img src="../images/xxam/qr_code.svg">`。
- テンプレの CSS: `background: url(../images/950037_logo.svg)`。CSS 自身（`css\`）から見た相対パスで書く。`url(images/…)` と書くと `css/images/…` になって表示されない。CSS の背景画像は PDF・画面内プレビュー・編集画面のどれにも出る。
- `style` 属性に書いた背景画像（`style="background:url(../images/…)"`）は PDF には出るが画面内プレビューには出ない。背景画像はテンプレの CSS か `<style>` に書く。
- 文書の置き場から見ない参照（`images/…` `css/…` 始まり）は扱わない。表示されず、「配信されない画像参照」の警告が出る。
- 画像を差し替えたあと、画面内プレビューへの反映はブラウザの再読み込みが必要（取得した画像はページを開いている間だけ覚えている）。

## 3.2 テンプレート生成器を置く

作成タブの「新規作成」は、既存のテンプレート生成器 `build.py`（Python のスクリプト）を、位置引数で `python <build.py> <Rep1 の委託会社コード> <ファンドコード> <基準日> [<コピー元ファンドコード> [<償還>]]` と起動する。基準日は editor が当日（日本時間。土日は直前の金曜）を `YYYY-MM-DD` で渡す（作成画面では指定できない）。コピー元を付けずに償還だけを付けるときは、コピー元の位置に空文字を入れる。`python` は PATH から探し、版は指定しない（3.13 かどうかは起動時の確認が知らせる）。生成器は editor のリポジトリには含まれず、社内の別サーバ・共有フォルダにある。editor は `python.script`（`PY_GENERATE_SCRIPT`）で `build.py` のパスを指す。既定のスクリプトはテスト用の偽物なので、本番では必ず設定する。

生成器は、作成画面のファンドの交付版・全体版の両方と、組入先（マザーファンド・組入投信）を書く（下の約束 6）。editor が `pending\` へ取り込むのは作る版だけで、作成画面で版種を選べばその版、選ばなければ作成済み・申請中でない版になる。組入先は版種の有無にかかわらず取り込まない。

置き方:

- 生成器を置くフォルダは、editor サーバの実行アカウントから**読み取り専用**にする。書き込めるのは生成器の保守者だけにする。生成器が出した HTML の JS は承認後は変えられない基準になるので、生成器を書き換えられる人は、サーバの実行アカウントでコードを実行できるのと同じ重みを持つ。
- `dataRoot` の配下には置かない。データの git リポジトリに実行コードが入り、data リポジトリを書ける人が任意のコードを実行できるようになる。
- 生成器の子プロセスへ渡す環境変数は `PATH` `SYSTEMROOT` `TEMP` `TMP` `PATHEXT` `COMSPEC` と、`PYTHONUTF8` `PYTHONIOENCODING` `TEMPLATES_DIR`（コピー元の確定版テンプレの読み先。サーバの `paths.templatesDir`）だけ。`PENDING_DIR` は渡さない（生成器は `pending\` に書かない）。生成器が他の環境変数（秘密値を含む）を読む前提にはしない。生成器はサーバの実行アカウントで動くので、`template\output\` と `template\log\` へ書けるよう、そのアカウントの書き込み権限を確かめる。

置き場所と出力: 生成器は `build.py` の 1 つ上の階層を基準にする。`build.py` が `<ルート>\template\src\build.py` にあるとき、結果は `<ルート>\template\output\<会社コード>_<ファンドコード>_<版種>.html` に書かれ、実行ログは `<ルート>\template\log\build_<Rep1 の委託会社コード>_<ファンドコード>_<基準日>.log` に書かれる。書き先もログの場所も `build.py` の位置から求めるので、editor 側に設定は無い。cwd は `build.py` のあるフォルダ（`template\src\`）。editor は取り込んだ出力ファイルと、版種を選んだときのもう片方の版の出力を `output\` から消す。組入先の出力と、版種を選ばずに飛ばした版（作成済み・申請中の版）の出力は消さずに残す。ログは消さない（運用者が後から読む）。同じ日に同じファンドを作り直すと、同じログの末尾へ追記される。

生成器側に求める約束（本番の生成器はこの 6 項目に合わせて改修してから、この版の editor を動かす）:

1. 成功したら終了コード 0 で終える。0 以外なら、editor は何も取り込まずに失敗にする（標準エラーを記録に残す）。
2. 実行ログは UTF-8 で書く。editor は起動時に `PYTHONUTF8=1` を渡す。editor はログを UTF-8 として厳格に読み、読めなければ失敗にする。
3. 書いたファイルは、ログに `[OUTPUT] <ファイル名>` の形で 1 行に 1 つ書く。`[OUTPUT] ` より前（日時・レベルなど）は自由で、editor は行の中の最初の `[OUTPUT] ` から行末までをファイル名として読む。印の無い行は普通のログとして読み飛ばす。ファイル名は `<会社コード>_<ファンドコード>_<版種>.html` の形で、区切り文字を含まない。
4. ログに書いたファイルは、終了する前に `output\` へ書き終えておく。ログにあって書かれていなければ、editor は全体を失敗にする。
5. ログは追記で書き、終了する前に閉じておく。editor は起動の前にログの長さを覚え、終了後に増えた部分だけを今回の分として読む。
6. 作成画面のファンドは交付版・全体版の両方を必ず書く（片方だけのファンドは無い）。組入先を書くときは、作成画面と同じ会社のファンドだけを、これも両版で書く。標準出力・標準エラーは自由で、editor は中身を解釈せず、失敗時の記録にだけ使う。

コピー元は `TEMPLATES_DIR` の `<会社コード>_<コピー元ファンドコード>_<版種>.html`（基準日なし）で、生成器はこれを読む。取り込む本数の上限は既定 50 本（`GENERATE_MAX_OUTPUT_FILES`、appconfig の `python.maxOutputFiles`）で、超えると全体を失敗にする。

editor は、ログの名前が `<会社>_<ファンド>_<版種>.html` の形で、会社が作成画面と同じで、空でなく、通常のファイルで、作成画面のファンドの作る版がそろっているときだけ取り込む。1 つでも外れたら何も取り込まない。作る版だけを `pending\` に入れ、組入先は取り込まずに `output\` に残す（作成画面の版種を選んだときの説明「<版>だけを作り、作成後はその編集画面が開きます。組入先は取り込みません。」で利用者に知らせる）。コピー元は、片方の版だけを作るときも両版がそろっていることを求める（生成器がコピー元の両版を読むため）。

運用上の注意とリスク:

- 生成器の `[OUTPUT]` 行の改修が済むまで、本番では生成できない。ログに `[OUTPUT]` 行が無ければ、editor は失敗にする。
- タイムアウトの既定は 5 分（300000 ms）。`PY_TIMEOUT_MS`（appconfig の `python.timeoutMs`。上限 600000 ms）で変える。
- 同じ会社の作成は 1 本ずつ実行する（組入先が同じ会社のファンドで共通のため、同時に書かせない）。この会社ごとの順番待ちは、生成の受付（同時 2・待ち 8）の外側にある。同じ会社の作成が続けて押されると、待ち 8 の数に入らずに順番を待つので、1 回 5 分かかる生成が重なった場合は、後ろの要求が長く HTTP 接続を握り続ける。目安として、同じ会社の作成が 4 本重なると最後の要求は 20 分ほど待つ。
- editor を動かしている間は、同じファンドの `build.py` を手で走らせない。同じ日のログへ追記が混ざり、editor が今回の分を切り分けられなくなる。editor の排他は editor の中の実行だけを覆う。
- 組入先の出力と、版種を選ばずに飛ばした版の出力は `output\` に残り続ける。editor はこれらを消さないので、溜まったものは運用者が確かめてから片付ける。
- 既知のリスク（ペア同期の初期差分）: 片方の版だけを作って承認したあと、もう片方の版を新しい雛形から作って承認すると、交付版⇄全体版のパーツ同期が同期履歴の無い状態で走る。中身の違うパーツはすべて「初期差分」の競合になり、自動同期が止まる。先に作った版でわざと消したパーツが、自動で挿入されて戻ることもある。両版を同時に作ればこの問題は起きないので、利用者には作成画面で版種を選ばずに両版を同時に作るよう勧める（操作手順書 第 4 章）。
- 既知のリスク（URL の意味の変化）: 作成画面の URL のクエリ `?editionType=交付版` の意味が、「両版を作って交付版を開く」から「交付版だけを作る」に変わった。古いブックマークから作成すると、交付版だけができる。

本番の端末での動作確認（本物の `build.py` に `[OUTPUT]` 行を足した後に行う）:

1. 作成タブで、まだ作成していない 1 ファンドを作成する。
2. 版種を選ばずに作成したときは、`dataRoot\pending\` に、そのファンドの交付版・全体版が `<会社>_<ファンド>_<版種>.html` で入ったことを確かめる。組入先は `pending\` に入らない。
3. 取り込んだファイルが `template\output\` から消えていることを確かめる。
4. `template\log\build_<Rep1 の委託会社コード>_<ファンドコード>_<基準日>.log` の末尾に、今回の実行の `[OUTPUT]` 行が追記され、文字化けしていないことを確かめる。
5. 組入先があるファンドでは、組入先の出力が `pending\` に入らず `template\output\` に残っていることを確かめる。版種を選んで作成したときは、選ばなかった版の出力も `output\` から消えていることを確かめる。

Python 3.13 を PATH に通す（本番機・開発機とも、運用者が手で設定する）:

1. Python 3.13 を入れる。インストーラで「Add python.exe to PATH」を選ぶと、ユーザー環境変数 PATH の先頭に `…\Python313\` と `…\Python313\Scripts\` が入る。
2. 手で設定するときは、スタートメニューで「環境変数」と検索して「環境変数を編集」を開き、ユーザー環境変数 `Path` に上の 2 つを足して、`%LOCALAPPDATA%\Microsoft\WindowsApps` より**上**へ移す。WindowsApps の `python.exe` は Microsoft Store の偽物で、先に当たると終了コード 9009 で起動できない。「設定 → アプリ → アプリ実行エイリアス」で `python.exe` / `python3.exe` をオフにしてもよい。
3. `setx` で PATH を設定しない。1024 文字で切れ、既存の PATH の後半が失われる。
4. Windows のプロセスの PATH は「システム環境変数 `Path` の後にユーザー環境変数 `Path`」の順で探す。システムの `Path` に別の版の Python があると、ユーザーの `Path` の先頭に置いても負ける。その場合はシステムの `Path` からその行を外す（管理者が行う）か、`PYTHON_BIN` に Python 3.13 の `python.exe` の絶対パスを設定する。起動時の確認が版違いとして警告するので、それで気づける。
5. 設定したら**新しいコマンドプロンプト**で `where python`（1 件目が Python 3.13 の `python.exe`）と `python --version`（`Python 3.13.x`）を確かめる。起動中のサーバには反映されないので、サーバも新しいコマンドプロンプトから起動し直す。
6. サーバをサービスや別のアカウントで動かす場合は、そのアカウントの PATH が使われる。そのアカウントで同じ設定をする。

設定を誤ったときは、サーバの起動ログ（下の表）と offline の setup（`offline\setup-offline.bat`）の警告が知らせる。

指紋（SHA256）の設定:

1. 生成器のスクリプトの指紋を取る: `certutil -hashfile \\fileserver\share\generator\generate_template.py SHA256`。2 行目の 64 桁の 16 進が指紋。
2. 環境変数 `PY_GENERATE_SCRIPT_SHA256`（または appconfig の `python.scriptSha256`）に設定し、editor を起動し直す。64 桁の 16 進でなければ起動を中止する。
3. 生成器を更新したら、指紋も取り直して設定し直す。設定し直すまで、生成は拒否される。利用者には「テンプレート生成器の指紋が設定と一致しないため、生成を中止しました。管理者に連絡してください」と表示され、サーバログには `[generate] 生成器の指紋が設定と一致しません` で始まるエラーが、監査ログには `template.generate` の失敗が残る。

照合できるのは入口のスクリプト 1 本だけで、そこから読み込まれるモジュールは対象外。モジュールの改ざんは、上の読み取り専用の運用で防ぐ。

起動ログの警告の意味（左の列は、各ログ行の先頭部分の引用。行の後ろには括弧書きで起動コマンドやスクリプトのパスが続く）:

| 起動ログ（…で始まる行） | 意味と対応 |
|---|---|
| `[generate] 生成器の Python: 3.13(python)` | 正常 |
| `[generate] 生成器の Python を起動できません` | PATH に `python` が無い、または Microsoft Store の偽物（WindowsApps。終了コード 9009）に当たっている。上の「Python 3.13 を PATH に通す」に従い、新しいコマンドプロンプトから起動し直す |
| `[generate] 生成器の Python が 3.12 です` | PATH で先に見つかる `python` が 3.13 でない（システムの `Path` にある別の版など）。PATH を直すか、3.13 の `python.exe` の絶対パスを `PYTHON_BIN` に設定する。appconfig に `python.args` が残っていれば外す（`python.exe` に余計な引数が付いて失敗するため） |
| `[generate] 生成器の指紋が未設定です` | 指紋を照合していない。共有フォルダ上の生成器を使うなら、上の手順で設定する |
| `[generate] 生成器が偽物(テスト用)のままです` | `PY_GENERATE_SCRIPT` / `python.script` が既定の `fake_generate_template.py` のまま。本番では既存の生成器を指す。設定し忘れると、本物ではない HTML が生成される |
| `[generate] 生成器のスクリプトを読めず指紋を照合できません` | 起動時ではなく、生成のたびに出るエラー（この表の他の行と違い、起動ログには出ない）。指紋を設定しているのにスクリプトを読めない（パス違い・共有フォルダへの権限不足）。生成は拒否される。`python.script` のパスと editor を動かすアカウントの読み取り権限を確かめる |

本物の生成器が使う Python パッケージは、Python 3.13 の本体（site-packages）へ入れる（`pip install --user` では入れない）。生成器は許可した最小限の環境変数だけで起動するため、利用者ごとの領域に入れたパッケージは見つからない。

どの警告でも editor は起動する（生成を使わない運用を止めないため）。生成の同時実行は `GENERATE_MAX_CONCURRENCY`（既定 2）、待ち行列は `GENERATE_MAX_QUEUE`（既定 8）で、超えた要求は「テンプレート生成の順番待ちが混み合っています」で返る。

## 3.2.1 帳票ツール create_report.py を置く（任意）

編集タブの「作成して開く」（検索欄に入力した、まだ帳票の無い基準日の値入り HTML を作る）と、値入り HTML の単体 PDF の組版は、本番の帳票ツール `create_report.py` を使う。
`report.script` を設定した環境だけで有効になり、未設定なら「作成して開く」は画面に出ず（編集タブの候補にも、`templates\` にだけある会社・ファンド・版種は出ない）、単体 PDF は今までどおり
vivliostyle で作る。生成器 `build.py` と同じく、editor のリポジトリには含まれず、社内の別サーバ・共有フォルダにある。

設定は `appconfig.json` の `report` の節か、環境変数で行う。

| 設定 | 環境変数 | 既定 | 意味 |
|---|---|---|---|
| `report.script` | `REPORT_SCRIPT` | なし（機能オフ） | `create_report.py` のパス |
| `report.scriptSha256` | `REPORT_SCRIPT_SHA256` | なし | スクリプトの SHA256（64 桁の 16 進）。設定すると起動のたびに照合し、食い違えば実行を拒否する |
| `report.timeoutMs` | `REPORT_TIMEOUT_MS` | 300000（上限 600000） | 1 回の起動の制限時間（ms） |

Python の実行ファイル（`PYTHON_BIN`）、子プロセスへ渡す環境変数、同時実行の枠（`GENERATE_MAX_CONCURRENCY` と
`GENERATE_MAX_QUEUE`）は、`build.py` と共有する。作成タブの生成と枠を取り合う。置き方の注意（読み取り専用にする、
`dataRoot` の配下に置かない）も 3.2 節と同じ。指紋は 3.2 節の手順と同じ要領で `certutil` で取る。

スクリプト側に求める約束（引数の 4 つの形・ファイル名・参照の封じ込め・単独の実行の git の扱い・終了コード・改ページの書き戻し）の正本は、設計書 7.5 節にある。本番の `create_report.py` は、その約束に合わせてから使う。運用で押さえる点は次のとおり。

- 引数の形は 4 つある。
  - `--html-only --fund-only`（単独の実行）: `filled\<id>.html` を書き、そのファイルだけを git にコミットする。
  - `--html-only --fund-only --from-editor`（編集タブの「作成して開く」）: `filled\<id>.html` を書くだけ。コミットは editor が、操作した利用者の名義で行う。
  - `--pdf-only --fund-only`（単独の実行と、承認のあとの正式 PDF）: ページ数を 4 の倍数にそろえる改ページを足した HTML を `filled\<id>.html` に書き戻し、`pdf\<id>.pdf` と 1 つのコミットで記録する。改ページを足した HTML が正の版になる。
  - `--pdf-only --fund-only --from-editor`（editor の単体 PDF）: 標準入力の HTML を組版し、PDF を標準出力に書く。`dataRoot` には何も書かない。
- 終了コードは、0 成功 / 2 引数の誤り / 3 入力が無い / 4 記録されていない変更がある（editor の承認の途中など） / 5 コミットに失敗した（`.gitattributes` に `*.pdf binary` が無い場合を含む）。それ以外の 0 以外は、その他の失敗として扱われる。
- `dataRoot` と git の場所は、スクリプト側の設定で持つ。`dataRoot` が editor と食い違うと、スクリプトが成功しても editor からは「出力が無い」になり、画面に「`create_report` の `dataRoot` の設定が editor と同じか確かめてください」と出る。git は editor の `GIT_BIN` と同じもの（遮断端末では同梱の PortableGit）を指す。
- 単独の実行のコミットに付くメール `<名前>@create_report.local` は、editor が承認のときに単独の実行のコミットと見分ける印なので、変えない。

スクリプトが `--from-editor` に対応していない（標準出力が `%PDF-` で始まらない）と、単体 PDF は「出力が PDF ではありません。create_report.py が `--from-editor` に対応しているか確かめてください」という失敗になる。DB が落ちているあいだは、`create_report` による単体 PDF は出せない（組版の違う PDF を黙って渡さないため、vivliostyle で代わりに出すことはしない）。

`pdf\` は `dataRoot` の直下に固定で、場所を変える設定は無い。git の管理下にあり、create_report.py が記録する。editor は `pdf\` をコミットせず、承認のコミットの前に、スクリプトがステージしたままの PDF を外す。editor は data リポジトリを用意するたびに（承認・編集タブの「作成して開く」・正式 PDF の組版の前。サーバの起動時には行わない）、`.gitignore` から `/pdf/` の行を外し、`.gitattributes` の先頭を `* text eol=lf`・`*.pdf binary` の 2 行にそろえる。`init-data-repo.ps1` も同じ内容で作る。

**承認のあとの正式 PDF。** 編集の申請を最終確定すると、editor が `... <版種> --pdf-only --fund-only` を裏で起動し、`pdf\<id>.pdf` を作る。承認した版と、ペア同期でパーツか CSS が写った相手の版が対象である。失敗しても承認は取り消されず、プレビュー画面の「正式 PDF を作り直す」（精査者・管理者）で同じ組版をやり直せる。画面に出る失敗の理由は利用者向けの文言だけで、詳しい内容はサーバのログにある。editor は組む前にも後にも古い `pdf\<id>.pdf` を消さない（組み直しが失敗しても、前回の PDF が記録として残る）。状態（`無い`・`古い`・`できた` など）は git の記録で決まり、成功と状態の判定の詳細は設計書 7.2 節にある。サーバを再起動したあとは、組み直すまで `古い` と出る id があることがある。

> [!WARN] CSS（`css\<会社>_<ファンド>_<版種>.css`）は基準日をまたいで共有される。承認で CSS が変わっても、editor が
> 作り直すのは承認した基準日とそのペアの版だけで、CSS を共有するほかの基準日の `pdf\<id>.pdf` は古い見た目のまま
> 残る。過去の基準日は発行済みで、作り直すと配布物と食い違うためである。必要な基準日があれば、運用者が単独の
> `--pdf-only --fund-only` で作り直す。

**入れる順番。** 次の順で入れる。(1) editor を上げる（このとき `report.script` はまだ未設定のままにする。`.gitignore` と `.gitattributes` は、上げたあとの最初の承認・編集タブの「作成して開く」・正式 PDF の組版で editor がリポジトリを用意するときに直る。`init-data-repo.bat` は履歴のあるリポジトリには触らないので、流し直しても直らない。それまでに単独の `--pdf-only` を流すと、`check-attr` で終了コード 5 で止まり、何も壊さない）、
(2) create_report.py を `filled` と PDF を 1 コミットで記録する版に直す、(3) `report.script` を設定する。
`--from-editor` に対応していない古いスクリプトを設定すると、「作成して開く」も単体 PDF も失敗する。editor より
先にスクリプトを直すと、まだ `.gitattributes` に `*.pdf binary` が無い。上の約束どおりに直したスクリプトなら、
`check-attr` で気づいて終了コード 5 で止まる（`check-attr` を確かめない作りだと、改行変換で壊れた PDF をコミットする）。`report.script` が未設定のあいだは正式 PDF の機能ごと無効なので、この順なら中途半端な状態で動くことが無い。

> [!WARN] **リポジトリが太る。** 正式 PDF を git に記録するので、data リポジトリは「承認の回数 × ペアの数 × PDF 1 本の
> 大きさ（数 MB）」ずつ増える。PDF は圧縮が効きにくく、差分もほとんど小さくならない。`dataRoot` をネットワークドライブに
> 置いている場合は、増えるほど clone と `git gc`、および editor の git の呼び出し（`GIT_TIMEOUT_MS` の既定は 30 秒）が
> 遅くなる。正式 PDF の状態の問い合わせも、1 回で git を 4〜6 本起こすので、履歴が増えるほど遅くなる（画面は
> 状態を繰り返し問い合わせる）。容量と `git count-objects -vH` を定期的に確かめ、時間切れが出るようなら `GIT_TIMEOUT_MS` を延ばすか、
> 古い履歴の整理を検討する。

**承認で止められない場合と、止めない場合。** 承認は、申請のあとに単独の実行で再作成された版を止める
（「申請後に再作成されました。」）。次の 2 つの場合は承認で止められず、警告か、履歴からの復元で補う。

- (a) 単独の実行のコミットが失敗した（終了コード 5）とき。印の付いたコミットが残らないので、承認を止められない。
  申請後に `filled\` が変わった警告だけが出る。
- (b) 再作成が、申請より前（編集画面を開いたあと、申請するまでの間）に起きたとき。承認の基準は申請した時点の履歴
  （`baseCommit`）で、編集画面を開いた時点ではないので止められない。承認の差分には値が戻る変更として現れる。

次の場合は、承認が止まる。

- (d) 承認後の正式 PDF を組んでいる間に、同じ版へ申請したとき。正式 PDF の改ページの書き戻しは単独の実行と同じ印で
  コミットされるので、その申請の承認は「申請後に再作成されました。」で止まる。正式 PDF が `できた` になってから
  編集画面を開き直し、申請し直す。

次の場合は、止めない方針にしている。

- (c) 承認済みの版を、あとから単独の実行が上書きすること。git の履歴から戻せる。承認の直後に書き換えられた場合だけ、
  承認の結果に警告が出る。

検証用の一時フォルダへ向け先を変える手段は無い。開発機と e2e では、偽物 `server/scripts/fake_create_report.py` を
設定し、本物の `create_report.py` を設定しない（本物の `dataRoot` を書き換える恐れがある）。

## 3.3 構築済み環境を新版へ上げる

構築済みの環境は、次の順で上げる。フォントの置き場の移設（`css\fonts`・`js`）と画像の置き場（`images`）は済んでいることが前提で、旧構成（`<dataRoot>\assets` にフォントと js を置き、CSS が `url(../fonts/…)` で参照する構成）からの移行パッチは廃止した。旧構成のまま新版を配置すると、フォントと JS が欠けた PDF が成功扱いで出る。

1. editor サーバを止め、新版を配置する。
   - あわせて、作成タブが読む `Rep1` の sproc を入れる（4.1 節）。`server\db\sproc\template.sql` と `series.sql` の仮のテーブル名・列名を実際の名前に合わせてから、`sqlcmd -S <host\instance> -d usrap -E -b -f 65001 -i server\db\sproc\template.sql`（`series.sql` も同じ）で流す。**流さないと作成タブの会社・ファンドが出ない。**
   - 新版で DDL や sproc が変わったときは、4 章の順（`ddl\` → `sproc\`。`seed\` は流さない）で流す。**サーバを起動する前に流す。** `part.sql` は必ず `01_テーブル.sql` の後に流す（4.2 節の注意）。
2. `editor\scripts\init-data-repo.bat` を流す（足りない置き場のフォルダだけを作る。履歴があれば git には触らない）。`dataRoot:` で始まる行（`dataRoot: …（読んだ元）`）の場所が、運用している dataRoot であることを確かめる（appconfig の `paths.dataRoot` が editor のフォルダの中を指して使わなかったときは、その案内がこの行より先に出る）。違う場所が出たら `-DataRoot <場所>` を付けて流し直す。
3. Python 3.13 が PATH で通っていることを、3.2 節の「Python 3.13 を PATH に通す」の手順 5 で確かめる（サーバをサービスや別のアカウントで動かす場合は、そのアカウントで確かめる）。続けて、本番の生成器の場所を `PY_GENERATE_SCRIPT`、指紋を `PY_GENERATE_SCRIPT_SHA256` に設定する（3.2 節）。
4. 新しいコマンドプロンプトから起動し、起動ログに `[generate]`（Python を起動できない・版が 3.13 でない・指紋が未設定・偽物のまま）の警告が出ていないことを確かめる。フォントを使うテンプレートで PDF を出し、フォントと JS が効いていることを確かめる。

# 4. SQL Server セットアップ（rest モード）

ターゲットは **SQL Server 2012**、DB `usrap`、既存スキーマ `ug01`、テーブル接頭辞 `Rep1_運報自動化_Editor_`。DB アクセスは 8 本のゲートウェイ sproc（第 1 引数 `@操作` で分岐）を通す（設計書 10.1 節参照）。

DDL/sproc/seed は `server/db/` に置く。

```
ddl/    01_テーブル.sql 02_索引.sql 03_制約.sql
sproc/  audit / noteMaster / part / sample / series / session / template / user の 8 本（DROP + CREATE）
dev/    Rep1_検証用.sql（検証用の Rep1）/ 台帳_削除.sql（旧テンプレート台帳の DROP）。apply.ps1 の対象外
seed/   管理ユーザー.sql（手順 1 で作る。リポジトリには無い）/ パーツカタログ.sql / 共通サンプル.sql（開発・検証用。本番へは流さない）
migrate/ 共通サンプル_分類登録.sql（共通サンプルの行を値なしで作る。apply.ps1 の対象外。4.3 節）
diag/   パーツ_Jinja構文調査.sql / パーツ_Jinja引数調査.sql（読み取りのみ。apply.ps1 の対象外。4.3 節）
```

> [!WARN] 全 SQL ファイルは **UTF-8 BOM 保存**（日本語識別子 + sqlcmd の cp932 対策）。SQL Server 2012 互換のため `CREATE OR ALTER` / `OPENJSON` / `FOR JSON` / `STRING_AGG` は不使用。

適用手順:

```
# 1) seed SQL を生成（管理ユーザーのパスワードハッシュ + seed）
#    パスワードは 8 文字以上。ログインIDと同じもの・admin・password は拒まれる
corepack pnpm --filter server exec tsx scripts/hash-password.ts admin "<パスワード>" 管理者 admin
corepack pnpm --filter server exec tsx scripts/gen-seed.ts

# 2) 適用（Windows 統合認証）
powershell -ExecutionPolicy Bypass -File server\db\apply.ps1 -Server <host\instance>
```

`apply.ps1` が ddl → sproc → seed の順に適用する。上の手順は開発機と検証用の DB の作り方で、本番では使わない。`管理ユーザー.sql` はリポジトリに置かない（git は無視する）。以前は `admin` のハッシュを置いていて、作らずに流すと既知のパスワードの管理者ができたため。seed を流すときにこのファイルが無ければ、`apply.ps1` は何も流さずに止まる。

> [!WARN] 本番では `seed/` を流さない。seed は開発・検証用の値（共通サンプルの開発値・検証用のパーツ・管理ユーザー）で、本番に流すと共通サンプルの全体共通などの行が開発値で埋まる。後で流す移行用スクリプト（4.3 節）は登録済みの組を飛ばすので、開発値がそのまま残る。本番で `apply.ps1` を使うときは `-SkipSeed` を付けて ddl → sproc だけを流す（`powershell -ExecutionPolicy Bypass -File server\db\apply.ps1 -Server <host\instance> -SkipSeed`）。sqlcmd の無い端末では SSMS で `ddl\01_テーブル.sql` → `02_索引.sql` → `03_制約.sql` → `sproc\*.sql` の順に開いて流し、`seed\` は開かない。

構築済みの検証用の DB に新しい seed を流し直すときは、先にパーツカタログの行を消す。seed は既存の行を上書きしないので、消さずに流すと `委託会社コード` が NULL のままの行が残り、どの会社のパーツ一覧も空になる。

## 4.1 Rep1 のファンド属性を読む sproc

作成タブの委託会社・ファンド・シリーズは、同じサーバの `Rep1` にあるファンド属性を、usrap の sproc（`template` の `委託会社一覧` / `ファンド一覧`、`series` の `一覧`）から 3 部名で読む。テーブル名と列名は仮で、sproc の中だけに書いてある。

| sproc が返す列（変えない） | 仮の読み元 |
|---|---|
| `委託会社コード` / `委託会社名` / `委託会社略称` | `Rep1.dbo.Rep1_投委託会社` |
| `ファンドコード` / `ファンド名` | `Rep1.dbo.Rep1_投信ファンド属性` |
| `ファンドコード` / `シリーズコード` | `Rep1.dbo.Rep1_投信ファンド属性` |

1. 実際のテーブル名・列名に合わせて、`template.sql` と `series.sql` の `FROM` と各列の元の名前を直す（`AS` の右の列名は変えない）。`委託会社略称` は、テンプレートのファイル名に使う会社コード（`XX01` / `xxam` など）に当たる列にする。
2. `template.sql` と `series.sql` を流す（上の `apply.ps1` か、1 本ずつ `sqlcmd … -i server\db\sproc\<ファイル>`）。
3. 確かめる: `sqlcmd -S <host\instance> -d usrap -E -f 65001 -Q "EXEC [ug01].[Rep1_運報自動化_Editor_usp_テンプレート] @操作=N'委託会社一覧'"` で、会社と略称が返ること。

作成タブで「データベース処理に失敗しました」と出るときは、次を疑う。

- `series.sql` を流し忘れていないか（会社・ファンドは出るのに、3 つ選ぶと失敗する）。
- editor を動かすアカウントが `Rep1` の 2 テーブルを読めるか（DB をまたぐ参照は所有権の連鎖が既定で効かないため、`Rep1` 側にそのアカウントの SELECT 権限が要る）。

旧版で作ったテンプレート台帳（`ug01.Rep1_運報自動化_Editor_テンプレート台帳`）は editor が読まなくなった。不要なら `server\db\dev\台帳_削除.sql` で消す（任意）。

## 4.2 パーツカタログの対象版種・英名・委託会社コード

パーツカタログには、パーツ一覧を編集中のテンプレートの版種で絞る `対象版種`、委託会社で絞る `委託会社コード`、別ツール用の `カテゴリ英名`・`大分類英名`・`中分類英名`・`小分類英名` の列がある。

| 列 | 型 | 意味 |
|---|---|---|
| `対象版種` | `NVARCHAR(32)` | パーツ一覧と分類候補に出す版種。NULL と空文字列は両版共通。値はテンプレートの版種と同じ文字列（`交付版` / `全体版`）で、固定しない |
| `委託会社コード` | `CHAR(5)` | パーツ一覧に出す委託会社（Rep1 の委託会社コード）。NULL のパーツは、どの会社の一覧にも出ない |
| `カテゴリ英名` `大分類英名` `中分類英名` `小分類英名` | `NVARCHAR(128)` | 別ツール用。editor は読まない |

版種を限りたいパーツに `対象版種` を入れる。NULL か空文字列のパーツは、どちらの版でも出る。入れたあとは、次の `一覧` を `@版種` に `交付版` と `全体版` を渡して流し、件数が意図どおりか確かめる。

`sqlcmd -S <host\instance> -d usrap -E -f 65001 -Q "EXEC [ug01].[Rep1_運報自動化_Editor_usp_パーツ] @操作=N'一覧', @版種=N'交付版'"`

```
-- 全体版のテンプレートでだけ出すパーツ
UPDATE [ug01].[Rep1_運報自動化_Editor_パーツカタログ]
   SET [対象版種] = N'全体版'
 WHERE [パーツID] IN (N'<パーツID>', N'<パーツID>');

-- 分類（カテゴリ）単位でまとめて交付版専用にする
UPDATE [ug01].[Rep1_運報自動化_Editor_パーツカタログ]
   SET [対象版種] = N'交付版'
 WHERE [カテゴリ] = N'<カテゴリ>';

-- 両版共通へ戻す
UPDATE [ug01].[Rep1_運報自動化_Editor_パーツカタログ]
   SET [対象版種] = NULL
 WHERE [パーツID] = N'<パーツID>';
```

英名も同じ書き方で入れる。分類は同じ名前の行が並ぶので、日本語名の列を条件にして行をまとめて更新する。

```
UPDATE [ug01].[Rep1_運報自動化_Editor_パーツカタログ]
   SET [カテゴリ英名] = N'<English>', [大分類英名] = N'<English>',
       [中分類英名] = N'<English>', [小分類英名] = N'<English>'
 WHERE [カテゴリ] = N'<カテゴリ>' AND [大分類] = N'<大分類>'
   AND [中分類] = N'<中分類>' AND [小分類] = N'<小分類>';
```

> [!WARN] `part.sql` は `01_テーブル.sql` の後に流す。`part.sql` は DROP してから CREATE するので、列が無い状態で先に流すと CREATE が失敗し、sproc が無い状態になる。

> [!WARN] `対象版種` の値は、テンプレートの版種（ファイル名の末尾の `交付版` / `全体版`）と同じ文字列にする。比較は列の照合順序（`Japanese_CI_AS`）に従うので、大文字小文字・全角半角の違いと末尾の空白は同じ値として扱われる。別の語（例: `交付`）を入れると、そのパーツはどちらの版でも出なくなる。NULL と空文字列は両版共通の意味になる。値の取り違えには DB 側の CHECK が無いので、入れたあとに上の `一覧` で件数を確かめる。

## 4.3 共通サンプルと値ファイル

作成タブ・プレビュー・比較・結合 PDF の差し込み値は、共通サンプルのテーブル（`Rep1_運報自動化_Editor_共通サンプル`）から読む。編集タブで挿入する Jinja のパーツは、テンプレートごとの値ファイルの値で描く。

- 共通サンプルの `データJSON` には、本番の変数名で値を入れる。トップレベルが object の JSON 断片で、同じキーを 2 つの行に持たせない（重なれば ID の小さい行が勝ち、作成タブで警告が出る）。editor は変数名を前提にしないので、本番のパーツが使う名前のまま入れる。
- パーツカタログに分類の組を足したときは、`migrate\共通サンプル_分類登録.sql` を SSMS で開いて流すと、足りない組の行が値なし（`{}`）で入る。既定はプレビューで何も書かない。結果タブで確かめてから、ファイルの中の `@実行` を 1 に書き換えて流し直す。登録済みの組は飛ばすので、何度流してもよい。
- パーツの `内容HTML` に editor の描画器が扱えない Jinja の構文が無いかは、`diag\パーツ_Jinja構文調査.sql` と `diag\パーツ_Jinja引数調査.sql` で調べる。読み取りだけで、構文の種類・件数・パーツ ID だけを出す（`内容HTML` の本文は出さない）。扱えない構文があれば、結果を開発側へ渡す。
- 値ファイルの置き場の既定は `<dataRoot>\json`（appconfig の `paths.jsonDir` か環境変数 `JSON_DIR` で変えられる）。ファイル名は編集タブのテンプレート ID（`会社_ファンド_基準日_版種`）に `.json` を付けたもの。editor はこのファイルを読むだけで書かない。無いテンプレートでも編集は開き、Jinja のパーツを挿入したときに空欄で描いて警告を出す。

# 5. 起動（モード別）

`start.bat` のモードで起動する。データの取り出し口は rest モードの 1 系統だけなので、データモードの引数は無い（旧 `rest` / `db` は無視され、旧 `local` は警告を出したうえで rest モードで起動する）。

| 用途 | コマンド |
|---|---|
| 開発（Fastify:24680 + Vite:24681） | `pnpm dev` または `start.bat dev` |
| 本番（ビルド後 :24680 単体） | `pnpm build` 後 `pnpm --filter server run start`、または `start.bat prod` |
| LAN 公開（本番 + REST + HTTPS） | `start.bat lan`（事前に `scripts\setup-lan-https.bat` と `scripts\setup-lan-firewall.bat` を各 1 回実行。詳細は editor/README.md「LAN 公開」節） |

`start.bat` は `AUTH_REQUIRED=true` / `AUDIT_DB=true` を設定して起動する。web は REST 実装の Repository で SQL Server に接続する。

ロールの内部名（DB・API・監査ログに出る名前）は、管理者 = `admin` ／ 精査者 = `approver` ／ 編集者 = `editor` ／ 閲覧者 = `viewer`。

## 5.1 無認証モードでの起動（server 単体の設定）

web のローカルモード（fixtures + localStorage）はもう無い。`AUTH_REQUIRED=false`（無認証モード。ログインなし）は server 単体の設定として残っているが、`start.bat` からは起動できない。使うときは環境変数を手で設定し、`start.bat` を通さずに起動する。PowerShell でリポジトリルートから実行する例:

```powershell
$env:AUTH_REQUIRED='false'; $env:AUDIT_DB='false'; pnpm dev
```

- `AUDIT_DB='false'` は監査ログを DB へ書かないための設定である（ファイルの監査ログは残る）。
- 無認証モードでは誰でもデータ系の API を使えるので、loopback（自分の端末）で待ち受けるときだけに使う。loopback 以外のホストで待ち受けようとすると `config.ts` が起動を拒否する。
- 設定した環境変数はその PowerShell のウィンドウを閉じるまで残る。通常の起動に戻すときはウィンドウを閉じるか、`Remove-Item Env:AUTH_REQUIRED, Env:AUDIT_DB` で消す。

> [!NOTE] rest モードに必要な msnodesqlv8 のネイティブバイナリ（N-API の公式 prebuild）は、6.0.0 から npm の tarball（`prebuilds\win32-x64\`）に入っているので、`.pnpm-store` からの `pnpm install --offline` だけで揃う。`offline/setup-offline.bat` は install の後に `require` で疎通を確かめ、読めなければ setup を失敗にする。

# 6. オフライン検証チェックリスト

1. **調達**: バンドル tar.gz（`.pnpm-store/`・`pnpm.tgz`・`ms-playwright/` 同梱）が生成される。
2. **遮断**: ネット遮断で `offline/setup-offline.bat` の展開〜`pnpm build` が完走、ネイティブ取得が走らない。
3. **起動**: `GET /api/health` → `{ok:true}`、ブラウザで SPA 表示、DevTools で外部通信なし。
4. **PDF（最重要）**: `POST /api/build` で PDF 生成成功、Edge 自動検出が機能、MathJax（数式描画）を読み込めなくても停止・失敗しない。
5. **生成/保存**: `POST /api/generate`・`PUT /api/templates/:id/draft`・`POST /api/review-requests`（確定保存の申請）が成功。
6. **エディタ UI**: GrapesJS のアイコン/スタイルに欠けがない。
7. **回帰**: `pnpm typecheck`・`pnpm check:ci` が通る（typecheck は `@editor/shared` 先行ビルドが前提）。
8. **DB ドライバ**: setup ログに「msnodesqlv8 ネイティブ .node を確認（require OK）」が出る（= `prebuilds\win32-x64\msnodesqlv8.node` を読める。DB 接続自体は 4 章の適用後に `POST /api/auth/login` で確認）。

# 7. 監査ログ

- 監査ログは `logs/audit.log`（`logging.level` / `logging.pretty` で制御）。rest モードでは `AUDIT_DB=true` で監査ログ sproc にも記録する。
- ログレベル既定は `info`（`LOG_LEVEL` で上書き可）。本番は `NODE_ENV=production` で Pretty 無効（`LOG_PRETTY` で上書き可）。

# 8. SQL エラーと HTTP の対応

`server/src/db/sproc.ts` が SQL エラーを HTTP へマップする。運用時の切り分けに使う。

| SQL エラー | 種別 | HTTP |
|---|---|---|
| `THROW 50404` | not_found | 404 |
| `THROW 50409` / 一意制約 2627・2601 | conflict | 409 |
| `THROW 50000` / `THROW 50400`（必須パラメタ不足等） | validation | 400 |
| その他 | unexpected | 500 |
