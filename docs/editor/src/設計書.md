本書は Editor（運報自動化テンプレート編集 Web アプリ）の構造・データ抽象化・編集エンジン・承認ワークフロー・フェーズ2（REST + SQL Server）を、TypeScript / Vue にまだ慣れていない読者でも実装を追えるところまで掘り下げて記述する。一次資料は `editor/README.md`・`editor/CONTRIBUTING.md`・`shared/src/` の型と Repository 契約・`server/` 各層。本文中のコード抜粋はすべて実ソースからの引用で、引用元をパスで示す。

# 1. 概要・目的

Editor は、Jinja2 で作成された HTML/CSS テンプレート（ファンド報告書系）を非エンジニアが GUI で安全に編集し、サンプルデータを差し込んでプレビュー・PDF 出力できる社内 Web アプリである。

- **編集**: GrapesJS（レイアウト/CSS 中心）。`{{ }}` / `{% %}` / `{# #}` を壊さず温存（mask/restore）。
- **プレビュー**: ブラウザ内 Nunjucks で生 Jinja2 + サンプルデータを描画 → vivliostyle でページ組み表示。
- **PDF**: サーバ側 `@vivliostyle/cli`（常駐ワーカープール）で生成。
- **作成**: 既存 Python 生成器を Fastify から `child_process` で呼び出し。
- **確定保存**: 編集者の**申請**を精査者（approver）が**承認**したときだけ本番テンプレートへ反映する 2 段階ゲート（9 章）。
- **認証**: 独自認証（ログイン + 初回パスワード初期化）。テーマはブルー系（Tailwind v4 + shadcn-vue）。

利用者ロールは 4 種: `admin`（全操作 + ユーザー管理）/ `approver`（精査者。承認・却下）/ `editor`（編集・申請）/ `viewer`（閲覧）。

# 2. 用語解説

| 用語 | 意味 |
|---|---|
| Jinja2 | Python 系のテンプレート言語。`{{ 変数 }}`・`{% if %}`・`{# コメント #}` を HTML に埋め込む。本ツールの編集対象。 |
| Nunjucks | Jinja2 とほぼ同じ文法の JavaScript 実装。ブラウザ内プレビューの描画に使う（近似であり完全互換ではない）。 |
| GrapesJS | ブラウザで動く WYSIWYG エディタ部品。HTML を DOM として編集するため、素の Jinja タグは壊れる。これを守るのが mask/restore（7 章）。 |
| Repository パターン | 「データの取得・保存」をインターフェースとして切り出す設計。画面はインターフェースだけに依存し、実装（localStorage / REST）を差し替えられる。 |
| DTO | Data Transfer Object。層をまたいで受け渡す入れ物の型（例: `DropdownQuery`）。 |
| Result 型 | 失敗を例外でなく戻り値で表す型。`{ok:true, value}` か `{ok:false, error}` のどちらか（4 章）。 |
| Zod | TypeScript のスキーマ検証ライブラリ。型定義と実行時検証を一体化でき、本ツールでは**型の正典**（4 章）。 |
| pnpm workspace | 1 リポジトリに複数パッケージ（shared/web/server）を置いて依存を共有する仕組み。 |
| Pinia store | Vue の状態管理。画面をまたいで持ちたい状態（ログインユーザー等）の置き場。 |
| composable | Vue の再利用ロジック関数（`useXxx`）。状態とふるまいをコンポーネントの外に切り出す。 |
| Fastify | Node.js の Web サーバフレームワーク。server パッケージの土台（10 章）。 |
| sproc ゲートウェイ | DB アクセスを対象ごとに 1 本のストアドプロシージャへ集約し、処理内容は第 1 引数 `@操作` で分岐させる方式（11 章）。 |
| vivliostyle | HTML+CSS を印刷用のページ（A4 等）に組版するライブラリ。ブラウザ内組版（`@vivliostyle/core`）と PDF 生成 CLI（`@vivliostyle/cli`）の両方を使う。 |
| 2 系統の原則 | 「編集タブ = 実値埋め込み済み HTML をハイライト無しで編集」「作成タブ = 共通サンプルで値入りに見せてハイライト有り」という本ツールの根幹規約（7.1 節）。 |

## 3.1 「1 リクエストの旅」— 属性ドロップダウン取得の縦貫例

画面の 1 操作がどの層をどう通るかを、代表例（編集タブの属性ドロップダウン）で追う。

| 段 | ファイル・関数 |
|---|---|
| 1. 画面 | `web/src/features/templates/components/SearchFilters.vue`（`useCascadingSelect` で 4 段カスケード） |
| 2. Repository | `web/src/api/rest/templateRepo.ts` の `getDropdownOptions` |
| 3. REST クライアント | `apiFetch(apiPaths.templatesOptions)` = `GET /api/templates/options` |
| 4. server route | `server/src/routes/templates.routes.ts`（`preHandler: requireAuth`） |
| 5. server repository | `server/src/repositories/templateRepo.ts` の `getDropdownOptions` |
| 6. DB | `callSproc(SP.template, '候補', ...)` → SQL Server |

server 側 5〜6 段の実装。sproc が返す縦持ち行（区分/値）を DTO へ整形するだけの薄い層になっている:

```ts
export async function getDropdownOptions(q: DropdownQuery): Promise<DropdownOptions> {
  const rows = await callSproc(SP.template, '候補', queryParams(q));
  const pick = (kbn: string) =>
    rows.filter((r) => asString(r.区分) === kbn).map((r) => asString(r.値));
  return { companyCodes: pick('会社'), fundCodes: pick('ファンド'),
           baseDates: pick('基準日'), editionTypes: pick('版種') };
}
```

> [!INFO] **DB の守備範囲**: DB は台帳（作成可能カタログ）・パーツ・認証・監査のみで、**テンプレート本体はファイル + git が正**。`listTemplates` / `getTemplate` は `data/templates` のファイル走査であり sproc を通らない。「本体=ファイル/git、DB=台帳」がフェーズ2 の基本方針。

もう 1 本の代表例「確定保存」は承認ゲートを通る: プレビュー画面の申請 → `POST /api/review-requests`（`data/reviews/` に保存、実ファイル非更新）→ 承認時に `applyConfirmedSave`（実ファイル書込 + git コミットの**唯一の関所**）。詳細は 9 章。

# 4. shared: 型の真実源

## 4.1 Result 型（`shared/src/result.ts`）

失敗を例外でなく値で運ぶ。全 Repository メソッドが `Promise<Result<T>>` を返すため、呼び出し側は `if (!res.ok)` の分岐だけでエラー処理が書ける:

```ts
export type Ok<T> = { ok: true; value: T };
export type Err<E> = { ok: false; error: E };
export type Result<T, E = AppError> = Ok<T> | Err<E>;

export const ok = <T>(value: T): Ok<T> => ({ ok: true, value });
export const err = <E>(error: E): Err<E> => ({ ok: false, error });

/** 成功値を変換する。エラーはそのまま素通しする。 */
export const map = <T, U, E>(r: Result<T, E>, f: (value: T) => U): Result<U, E> =>
  r.ok ? ok(f(r.value)) : r;
/** Result を返すステップを連結する。最初のエラーで短絡する。 */
export const andThen = <T, U, E>(r: Result<T, E>, f: (value: T) => Result<U, E>): Result<U, E> =>
  r.ok ? f(r.value) : r;
```

## 4.2 AppError（`shared/src/errors.ts`）

エラーは 7 種の `kind` に正規化する。`message` は常にユーザー表示可能な日本語、技術詳細は `cause`（ログ専用）に隔離する:

```ts
export type AppErrorKind =
  | 'not_found' | 'validation' | 'unauthorized'
  | 'forbidden' | 'conflict' | 'network' | 'unexpected';

export interface AppError {
  kind: AppErrorKind;
  message: string;      // ユーザー向け・日本語。常に表示して安全
  cause?: unknown;      // ログ専用 — ユーザーには出さない
  code?: string;        // 機械可読の任意コード 例 'USER_DISABLED'
}
```

`toAppError(cause)` が「throw されたもの → AppError」の継ぎ目で、既に AppError ならそのまま返す。

## 4.3 ドメイン型は Zod スキーマが正典

主要なドメイン型は `shared/src/schemas.ts` の **Zod スキーマが正典**で、`shared/src/index.ts` は `z.infer` で TS 型を導出する。手書き interface での二重定義はしない（手書きの例外は `FundResolution` / `ConfirmSaveRequest` / `TemplateInstance` のみ）。スキーマは実行時検証（server の `validate.ts`）と OpenAPI 生成（zod-openapi）にも共用される:

```ts
export const Template = z.object({
  meta: TemplateMeta,
  html: z.string().meta({ description: 'Jinja2 生 HTML(タグ保持)' }),
  css: z.string().meta({ description: 'fundCode ごとの共有 CSS' }),
  filled: z.string().meta({ description:
    'エディタキャンバス用に事前描画した filled HTML(Jinja 値を差し込みつつ元ソースを保持)。' +
    '静的な fill が無ければ空で、エディタは都度描画にフォールバックする' }),
}).meta({ id: 'Template' });

export const UserRole = z.enum(['admin', 'approver', 'editor', 'viewer']);
```

- **テンプレート同一性**: `TemplateAttributes`（`companyCode` 委託会社 / `fundCode` ファンド / `baseDate` 基準日 yyyymmdd / `editionType` 版種）。ファイル名規約 `company_fund_date_edition.html` の変換は `shared/src/domain/template.ts`（`templateFileName` / `parseTemplateFileName`）の純関数。
- **履歴 3 種**（編集 / PDF 出力 / 作成）+ パーツ単位 `PartHistoryEntry`、**版スナップショット**（`TemplateSnapshot` / `TemplateVersionMeta`）、**パーツカタログ**（`PartClassification` 4 段 / `PartCatalogItem`）、**承認系**（`ReviewRequestMeta` / `ReviewRequest` 等。9 章）。

## 4.4 Repository 契約 — 全 7 種

画面/サービス/ストアは**集約ごとの Repository インターフェース**（`shared/src/repositories/*`）にのみ依存する。全メソッドは `Result<T>` を返す。

| Repository | メソッド |
|---|---|
| `AuthRepository` | `login` / `logout` / `me` / `initPassword` |
| `TemplateRepository` | `getDropdownOptions` / `listTemplates` / `getTemplate` / `generate` / `resolveFund` / `listSeriesFunds` / `saveDraft` / `getDraft` / `discardDraft` / `confirmSave` / `getSampleData` |
| `HistoryRepository` | `getEditHistory` / `getPdfHistory` / `getCreateHistory` / `recordPdfExport` / `listVersions` / `getSnapshot` |
| `PartRepository` | `getPartClassificationOptions` / `listParts` / `listPartHistory` / `recordPartChange` |
| `UserRepository` | `listUsers` / `createUser` / `updateUser` / `resetUserPassword` |
| `NoteRepository` | `listNotes` / `saveNote`（`content` 空文字＝削除） |
| `ReviewRepository` | `submitReview` / `listReviews` / `getReview` / `approveReview` / `rejectReview` |

承認ゲートの核となる `ReviewRepository` の契約（`shared/src/repositories/ReviewRepository.ts`）:

```ts
export interface ReviewRepository {
  /** 確定保存を申請する(pending 作成・実ファイル非更新)。 */
  submitReview(req: SubmitReviewRequest): Promise<Result<ReviewRequestMeta>>;
  /** 申請一覧(承認キュー)。状態で絞り込める。 */
  listReviews(filter?: ReviewListFilter): Promise<Result<ReviewRequestMeta[]>>;
  /** 申請 1 件を本体込みで取得する(承認画面のプレビュー用)。 */
  getReview(reqId: string): Promise<Result<ReviewRequest>>;
  /** 承認して実ファイルへ反映する(approver|admin のみ)。反映後メタ + 並行性警告を返す。 */
  approveReview(reqId: string, decision: ReviewDecisionRequest): Promise<Result<ApproveReviewResult>>;
  /** 却下する(approver|admin のみ)。理由は decision.comment。 */
  rejectReview(reqId: string, decision: ReviewDecisionRequest): Promise<Result<ReviewRequestMeta>>;
}
```

## 5.1 差し替え点（`web/src/api/repositories.ts`）

フェーズ1（localStorage）とフェーズ2（REST）は**同じ Repository 契約**を満たすため、束ねオブジェクトの差し替えだけで切り替わる。画面コードは無改修:

## 5.2 同一メソッドの local / rest 対比（`getTemplate`）

local 実装は localStorage の上書き + fixtures（`web/src/api/local/templateRepo.ts`）:

```ts
getTemplate: (id: string) =>
  attempt(() => {
    const meta = allMetas().find((m) => m.id === id);
    if (!meta) throw notFound(`テンプレートが見つかりません: ${id}`);
    const htmlOverride = read<Record<string, string>>(K.htmlOverride, {});
    const cssOverride = read<Record<string, string>>(K.cssOverride, {});
    const html = htmlOverride[id] ?? fixtureTemplates[meta.fileName] ?? '';
    const css = cssOverride[meta.attributes.fundCode] ?? fixtureCss[meta.attributes.fundCode] ?? '';
    // 静的 filled は未編集 fixture のみ有効。override 済みなら editor が再 fill。
    const filled = htmlOverride[id] ? '' : (fixtureFilled[meta.fileName] ?? '');
    return delay({ meta, html, css, filled });
  }),
```

rest 実装は REST への委譲のみ（`web/src/api/rest/templateRepo.ts`）:

```ts
getTemplate: (id: string) =>
  attemptRest(() => apiFetch<Template>(buildPath(apiPaths.templateById, { id }))),
```

「throw → Result」の継ぎ目は共通ヘルパー（local が `attempt`、rest が `attemptRest`）に集約。REST トランスポート `apiFetch`（`web/src/api/rest/http.ts`）は `credentials: 'include'`・`/api` プレフィックス付与・HTTP エラー→AppError 変換（サーバの `{kind, message, code}` を優先、無ければ status→kind 表）を一手に担う。

## 5.3 ローカル fixtures と genFilled（2 系統の原則のデータ源）

編集タブが読む「値埋め込み済み HTML」は、`web/scripts/genFilled.ts`（`pnpm --filter web run gen:filled`）が事前生成する:

```ts
function resolveSample(fundCode, editionType): SampleData {
  const file = resolve(sampleDir, `${fundCode}.json`);
  if (existsSync(file)) {                       // ファンド別実値を正典に
    const real = JSON.parse(readFileSync(file, 'utf8')) as SampleData;
    return applyEdition(real, editionType);     // 版種だけファイル名由来で上書き
  }
  return buildSampleData(funds[fundCode], fundCode, editionType); // 無ければ共通ダミー
}
```

入力は `fixtures/templates/*.html`（生 Jinja）+ `fixtures/sample/<fund>.json`（**per-fund 実値**）、出力は `fixtures/filled/*.html`（= `Template.filled`）。**filled を全ファンド共通ダミーに潰してはならない**（編集タブが実値を失う退行。7.1 節のガードテストが機械検証する）。

# 6. フロントエンド構成

## 6.1 ルーティングと authGuard（`web/src/router/index.ts`）

- public: `/login`, `/password-init`（`meta.public`）。
- `MainLayout` の子: `edit`（`/` 既定）/ `create` / `compare` / `reviews`・`reviews/:reqId` / `history` / `admin`（`meta.admin`）。
- 全画面ルート: `/edit/:id`（エディタ）と `/preview/:id`（プレビュー）。

ガードは `beforeEach` 本体を関数として切り出し、auth ストアを引数注入してテスト容易にしている:

```ts
export async function authGuard(to, auth: AuthGuardState = useAuthStore()) {
  if (!auth.ready) await auth.bootstrap();
  if (to.meta.public) return true;
  if (!auth.isAuthenticated) return { name: 'login', query: { redirect: to.fullPath } };
  if (auth.mustChangePassword && to.name !== 'password-init')     // 初回PW変更を強制
    return { name: 'password-init', query: { username: auth.user?.username ?? '', redirect: to.fullPath } };
  if (to.meta.admin && !auth.isAdmin) return { name: 'edit' };
  return true;
}
```

# 7. 編集エンジン詳解

## 7.1 編集 2 系統の原則（根幹）

編集体験は 2 系統あり、これはツールの根幹規約である。

| | 編集タブ（既存編集） | テンプレ作成タブ（新規作成） |
|---|---|---|
| 経路 | `EditTabView` → `/edit/:id`（query なし） | `CreateTabView` → `/edit/:id?created=1` |
| キャンバスに載る HTML | `tpl.filled`（**per-fund 実値**の値埋め込み済み HTML） | `toFilled(tpl.html, 共通sample)`（表示のみ値入りに見せる） |
| 差し込み値ハイライト | **出さない**（値は実値であり地の本文） | **出す**（placeholder の可視化） |

経路の見分けは一貫して `route.query.created === '1'`。実装上の出し分けは `useTemplateEditor.ts` の 1 行と、`useGrapes.ts` の `setVarsHighlight` に集約される:

```ts
g.init({ canvas, layers });
g.load(res.value.editableBody, res.value.css);
// 差し込み値ハイライトは作成経路(?created=1)でのみ。編集経路は実値編集なので出さない。
g.setVarsHighlight(route.query.created === '1');
```

```ts
function setVarsHighlight(on: boolean): void {
  varsHighlight = on;
  editor.value?.Canvas.getBody()?.classList.toggle('jinja-vars-highlight', on);
}
```

ハイライト CSS は `jinjaComponents.ts`。**素の `.jinja-chip.jinja-var` に背景を直書きせず**、body に `jinja-vars-highlight` クラスが付いたときだけ効かせる（直書きすると編集タブへハイライトが漏れる）:

```css
/* 素の値チップは本文と同化（両系統で常時）。背景は直書きしない */
.jinja-chip.jinja-var { display: inline; padding: 0; border: 0; color: inherit;
  font-family: inherit; font-size: inherit; white-space: normal; }
/* 差し込み値ハイライト（薄い琥珀）は作成経路だけ */
.jinja-vars-highlight .jinja-chip.jinja-var {
  padding: 0 1px; border-radius: 3px; background: rgba(245, 158, 11, 0.16);
  box-decoration-break: clone; }
```

> [!WARN] 退行ガードテスト `web/test/twoSystems.guard.test.ts` が「①素のチップに background 直書きが無い ②`.jinja-vars-highlight` 配下のみ背景定義 ③異なるファンドの filled で値が異なる（共通ダミー化していない）」を機械検証する。この 3 条件を壊す変更は禁止。

## 7.2 Jinja タグ保護 — jinjaMask（`web/src/lib/jinjaMask.ts`）

GrapesJS は HTML を DOM として扱うため、素のままでは Jinja タグが壊れる。編集前に **mask**（安全な表現へ変換）し、保存時に **restore**（元へ戻す）する。

- `toEditable(raw)`: ① `absorbBlocks` が `{% for %}<tr>…{% endfor %}` のようなブロックタグを、囲む要素の `data-jinja-open/close`（base64）属性へ吸収 → ② `wrapInlineTokens` がテキスト中の `{{ }}` を `<span data-gjs-type="jinja-var">` チップに包む。**属性内の Jinja は無変換で round-trip** する:

```ts
function wrapInlineTokens(html: string): string {
  const parts = html.split(/(<[^>]*>)/);
  return parts.map((part) => {
    if (part.startsWith('<')) return part;          // タグ — 属性はそのまま
    return part.replace(TOKEN_RE, (token) => {
      const kind = tokenKind(token);
      return `<span data-gjs-type="jinja-${kind}" class="jinja-chip jinja-${kind}" data-jinja="${b64encode(token)}">${htmlEscape(token)}</span>`;
    });
  }).join('');
}
export function toEditable(raw: string): string {
  let s = raw;
  s = absorbBlocks(s, 'for', 'endfor');
  s = absorbBlocks(s, 'if', 'endif');
  s = wrapInlineTokens(s);
  return s;
}
```

- `toTemplate(editable)`: 逆変換。Jinja トークンを一旦 Unicode 私用領域の placeholder に退避してから（必要なら js-beautify で整形し）最後に文字列置換で復元する。これにより HTML シリアライザが `<` `>` `&` をエスケープして Jinja を壊す事故を防ぐ。

## 7.3 GrapesJS 統合（`useGrapes.ts` / `jinjaComponents.ts`）

- `init` は `grapesjs.init({ storageManager: false, panels: { defaults: [] }, ... })` で GrapesJS の標準 UI と保存機構を全て無効化し、自前の 3 ペイン UI に統合する。`ed.Keymaps.removeAll()` で標準キーマップも外す（Undo/削除を自前系に一本化）。CDN 非依存（`cssIcons: ''`、アイコンフォントはローカル同梱）。
- コンポーネント型は `jinja-var`（差し込み値・draggable）/ `jinja-stmt`（条件・繰り返し。移動不可）/ `jinja-comment` / `jinja-script` / `jinja-math`。いずれも `editable: false` で中身のタグ文字列を保護する。

## 7.4 編集画面のオーケストレーション

- **`useTemplateEditor`**: テンプレのロード〜GrapesJS 初期化〜ライフサイクル統括。ロードは `templateEditorService.loadForEdit`:

```ts
async loadForEdit(id) {
  const tplRes = await templates.getTemplate(id); ...
  const draftRes = await templates.getDraft(id);        // draft を最優先
  const filledBody = tpl.filled || (await htmlWorker.toFilled(tpl.html, sample)); // 静的 filled 優先
  const editableBody = draft ? draft.html : getBodyInner(filledBody);
  const css = draft ? draft.css : tpl.css;
  return ok({ template: tpl, editableBody, css, parts: partsRes.value, fundName, hasDraft: !!draft });
}
```

- **`useAutosave`**: `Result` を返す保存関数を 800ms debounce で呼ぶ。状態は `idle | saving | saved | error`、失敗は必ずログし、toast は error への遷移エッジで 1 回だけ（debounce 毎に鳴らさない）。
- **`useSnapshotHistory`**: 自前 Undo/Redo。GrapesJS 純正 UndoManager は programmatic なスタイル変更を追えないため、`{html, css}` の不透明スナップショット方式にしている（上限 100）。past/future 配列は `editorSession` ストアと参照共有し、画面往復でも履歴が残る。

# 8. プレビュー / PDF / テンプレ生成

## 8.1 ブラウザ内プレビュー

- `web/src/lib/nunjucksRender.ts`: 生 Jinja2 + サンプルデータを Nunjucks（`autoescape: true`）で近似描画し、sanitize（DOMPurify）・外部 `<link>` 除去・CSS インライン化を経てプレビュー用ドキュメントを組み立てる。プレビュー専用で確定ファイルには影響しない。
- `PreviewView.vue` → `PreviewPanel.vue` が `@vivliostyle/core` で**ブラウザ内**ページ組版する（`data-vivliostyle-page-container` 要素を生成）。トンボは `lib/cropMarks.ts`。

## 8.2 PDF 生成（サーバ）

`server/src/vivliostyle/build.ts` の `buildInlinePdf` が入口（`POST /api/build`）。既定は**常駐ウォームワーカープール**（`buildWorkerServer.ts` / `buildWorkerPool.ts`）で、重い `@vivliostyle/cli` の import を 1 回に抑えて 2 回目以降を高速化する。`config.vivliostyle.build.poolSize <= 0` にするとジョブごとに `child_process` を spawn する保守的モードへフォールバックする（timeout 必須）。

プロジェクトプレビュー API は `previewManager.ts`（Vite サーバ起動 + reverse proxy で `/api/preview/:id` へ origin 書き換え、idle TTL / maxSessions 管理）。

## 8.3 テンプレ生成（Python アダプタ）

`server/src/generate/pyTemplate.ts` が既存 Python 生成器を `execFile(python, [script, JSON.stringify(attrs)])` で呼び、stdout の HTML を受け取る（`PYTHONUTF8=1`）。現状の `generate_template.py` は JSON-in/HTML-out のプレースホルダで、本番統合時に実物へ差し替える。

## 8.4 Worker オフロード（`web/src/workers/`）

HTML の重い処理（diff 構築・toTemplate・toFilled・Jinja 描画）は linkedom + comlink の **Vite module worker** へオフロードする。Worker chunk の不達・ハング・onerror を検知すると `createFallbackWorker` が **main-thread 実装へ恒久フォールバック**する（30 秒タイムアウト + broken シグナルの race）。オフライン/本番でプレビューが白紙になる既知事象はこのフォールバックで回避する。

# 9. 承認ワークフロー

確定保存は「編集者が申請 → 精査者（approver）が承認したときだけ実ファイルへ反映」の 2 段階ゲート。設計経緯は `docs/editor/承認ワークフロー設計.md` を参照（本章は実装の現状を正とする）。

## 9.1 ドメインと状態遷移

`ReviewStatus` = `pending | approved | rejected`。`ReviewOrigin` = `edit | create`（どちらの系統からの申請かを保持）。申請本体（`ReviewRequest`）は html / css / filledHtml を含み、一覧用の `ReviewRequestMeta` と分離している。

```
[編集 or 作成] → 申請 submitReview → pending ─ 承認 approveReview → approved（実ファイル反映 + git）
                                        └ 却下 rejectReview  → rejected（実ファイル非更新・理由必須）
```

## 9.2 データフロー

1. **申請**: プレビュー画面の「確定保存を申請」→ `PreviewView.submitForReview`（`origin = route.query.created === '1' ? 'create' : 'edit'` — ここでも 2 系統を判定）→ server `reviewRepo.submitReview` が `status: 'pending'` と `baseHash`（現行公開版の sha1）を記録して `data/reviews/` に保存する。**実ファイルは変更しない**。
2. **一覧**: 承認キュー（`ReviewQueueView`）。approver/admin は全件、editor は自分の申請のみ見える。
3. **精査**: `ReviewDiffView` がパーツ単位（`.page` 直下ブロック）で「変更前｜変更後」を並べる。diff 計算は版比較と同じ `htmlWorker.buildHtmlDiff` を共有。`edit` 申請の比較元は現行公開版、`create` 申請は空（全パーツ追加扱い）。
4. **承認**（approver/admin のみ）: `reviewRepo.approveReview` の要点は次の 4 つ。pending 以外は 409 / **自己承認拒否**（admin 除く）/ `staleWarning`（申請後に公開版が変わっていたら警告。ブロックはしない）/ `applyConfirmedSave`（実ファイル書込 + git 1 コミット）:

```ts
if (review.status !== 'pending') throw conflict(`この申請は既に${...}済みです`);
if (review.submittedBy === actor.username && actor.role !== 'admin')
  throw forbidden('自分の申請は承認できません(職務分掌)');
const staleWarning = review.baseHash !== null &&
  review.baseHash !== (await currentBaseHash(review.templateId, review.fundCode));
const meta = await applyConfirmedSave({ ...review, commitMessage, author: actor.username });
```

git コミットメッセージは `確定保存(承認): <id> 申請=<submitter> 承認=<approver>` で、申請者・承認者の双方が版管理に残る。

5. **却下**: 実ファイル非更新。理由（`decision.comment`）必須で、申請者に表示される。

## 9.3 施錠と監査

- ルート側は `requireApprover`（approver/admin 以外 403）を approve/reject に付け、`applyConfirmedSave` を呼べる経路を承認ハンドラに限定する。
- 監査ログは `review.submit` / `review.approve` / `review.reject` のイベント名で記録する。
- 申請の保管はファイル方式（`data/reviews/`）。DB sproc の追加はしない（「本体=ファイル/git」方針と整合し、オフラインでも動く）。

> [!INFO] 関連する `NoteRepository` はパーツ単位のメモ（版インスタンス単位、構造パスキー `pathKey`）。承認画面の行ラベルと編集画面のパーツ語彙（`partKey.ts`）を共有する基盤でもある。

# 10. サーバ構成（Fastify）

サーバは **Fastify** で構成する（`fastify` / `@fastify/cookie` / `@fastify/helmet` / `@fastify/static`）。

## 10.1 起動シーケンス（`server/src/app.ts`）

1. `Fastify({ loggerInstance: pino, bodyLimit: 8MB })` を生成し、`decorateRequest('user')`。
2. zip アップロード用の contentTypeParser（上限 64MB、超過は validation 400）。
3. `setErrorHandler(errorHandler)` — throw された AppError を HTTP status へ正規化する一元窓口。
4. `register(helmet)` / `register(cookie)`。
5. `GET /api/health` を直付け。
6. ルート群を `{ prefix: '/api' }` で register（10.2 節の 9 本 + openapi）。
7. `@scalar/fastify-api-reference` で `/api/docs`（API リファレンス UI。オフライン動作可）。
8. `APP_EPOCH = Date.now()` を SPA shell（index.html）へ注入し `no-store` で配信。本番静的配信は assets を immutable、SPA フォールバックは notFoundHandler。
9. `config.requireAuth` が真なら `invalidateAllSessions()` — **サーバ再起動で全セッション失効**（12 章）。
10. `app.listen({ port, host: '127.0.0.1' })`。SIGINT/SIGTERM でプレビュー/ワーカーを dispose する graceful shutdown。

# 11. DB アクセス層

## 11.1 sproc ゲートウェイ方式

ターゲットは **SQL Server 2012**、DB `usrap`、スキーマ `ug01`、テーブル接頭辞 `Rep1_運報自動化_Editor_`。すべての DB アクセスは対象ごとに 1 本のストアドプロシージャを通し、処理内容は第 1 引数 `@操作` で分岐させる。物理名（日本語）は `sprocNames.ts` の 1 箇所に集約する:

```ts
const SCHEMA = 'ug01'; const PREFIX = 'Rep1_運報自動化_Editor';
const gw = (target) => `[${SCHEMA}].[${PREFIX}_usp_${target}]`;
export const SP = {
  template: gw('テンプレート'), user: gw('ユーザー'), session: gw('セッション'),
  part: gw('パーツ'), sample: gw('サンプルデータ'), audit: gw('監査ログ'),
} as const;
```

`callSproc` は `EXEC <proc> @操作=?, ...` を**位置指定バインド**で発行する（SQL インジェクション回避）。SQL エラーは `Result` の `kind` へマップする:

```ts
function mapSqlError(e: unknown): AppError {
  const num = sqlNumber(e);
  const msg = sqlMessage(e);
  if (num === 50404) return notFound(msg ?? '対象が見つかりません');
  if (num === 50409 || num === 2627 || num === 2601)
    return conflict(msg ?? 'すでに存在するか、競合しています');
  if (num === 50000 || num === 50400) return validation(msg ?? '入力が正しくありません');
  return unexpected('データベース処理に失敗しました', { cause: e });  // 未知 → 500
}
```

（sproc 側が `THROW 50404` すれば HTTP 404、`50409` や一意制約違反 2627/2601 は 409、`50000`/`50400` は 400 になる。）

## 11.2 DDL / seed の運用（`server/db/`）

- `ddl/`（テーブル・索引・制約）→ `sproc/`（6 本）→ `seed/`（管理ユーザー = `hash-password.ts` 生成物、パーツカタログ・サンプルデータ = `gen-seed.ts` 生成）を `apply.ps1`（`sqlcmd -E -f 65001`）で順適用する。
- 全 `.sql` は **UTF-8 BOM** 保存（日本語識別子 + sqlcmd の cp932 対策）。
- SQL Server 2012 互換のため `CREATE OR ALTER` / `OPENJSON` / `FOR JSON` / `STRING_AGG` は不使用（sproc は DROP+CREATE、JSON はテキスト列に保管して Node 側でパース）。

## 11.3 接続（msnodesqlv8）

接続文字列は `Driver={ODBC Driver 17 for SQL Server};Server=...;Database=usrap;Trusted_Connection=yes`（**Windows 統合認証**、資格情報は保存しない）。ネイティブドライバ `msnodesqlv8` は optional dependency で、`server/src/db/pool.ts` に隔離する。

# 12. 認証

- **ログイン**: `POST /api/auth/login` → user sproc で照合 → セッション作成（session sproc `'作成'`）→ cookie `editor.sid`（乱数 id のみ・HttpOnly・TTL 既定 12h）。セッション本体は **DB 保管**で、リクエスト毎に `getSessionUser`（`'取得'`）が解決する。
- **初回パスワード初期化**: 新規ユーザーの初期パスワードはユーザー ID と同一。`mustChangePassword` が立っていると authGuard が `/password-init` へ強制誘導する（6.1 節）。ハッシュは `server/scripts/hash-password.ts` で生成して seed に投入。
- **再起動失効**: REST モードは起動フックの `invalidateAllSessions`（session sproc `'全失効'`）。ローカルモードは `web/src/lib/appEpoch.ts` が「配信側の起動 epoch（SPA shell に注入）とログイン時 epoch の食い違い」を検知して旧セッションを破棄する。これにより両モードで「サーバ/dev 再起動 = 全員再ログイン」の挙動が等価になる。再ログイン画面には再起動バナーを表示する。
