# 技術選定: バリデーションライブラリ比較（zod 代替調査）

> 開発者向けの技術判断メモ。配布用 docx ではなく Markdown 正典として扱う。
> 調査日: 2026-06-27。

## 背景（なぜ調べたか）

`editor/server` は現在 **zod ^4.4.3** をバリデーション基盤に採用している。次の3点を
動機に、`ArkType` / `Valibot` 等の代替を評価した。

1. 性能・将来性の妥当性確認
2. バンドルサイズ削減の余地
3. 今後 `editor/web`（Vue/Vite SPA）にクライアントバリデーションを追加する布石

結論を先に書くと、**サーバは zod 4 継続が妥当**、**フロント追加時はそのレイヤだけ
`Valibot` を検討**、が本リポジトリへの推奨である。

## 現状の zod 使用実態

- **使用範囲はサーバ専用**。`editor/server` の 13 ファイルのみ。`editor/web` /
  `editor/shared` / `graph-editor` は zod 非依存で、フロントにクライアント
  バリデーションは未実装。
- **`zod-openapi ^5.4.6` と密結合**（最大のロックイン）。`z.enum().meta({ id })` 等の
  zod4 固有 API でスキーマにメタデータを付け、`createDocument()` で OpenAPI 3.1 を
  自動生成している。
  - 代表: `editor/server/src/openapi/schemas.ts`, `editor/server/src/openapi/document.ts`
- 使用している zod4 固有 API: `z.prettifyError`（`editor/server/src/middleware/validate.ts`）、
  `.meta()`, `.strict()`, `.partial()`, `safeParse`, `z.infer`, `z.enum`。
- 主なパターン:
  1. 環境設定検証（`editor/server/src/config.ts`）
  2. Express ボディ検証ミドルウェア（`editor/server/src/middleware/validate.ts`）
  3. ルート単位スキーマ＋`z.infer`（各 `editor/server/src/routes/*.routes.ts`）
- TS 構成: `editor/tsconfig.base.json` で `strict: true` / `target ES2022`、サーバは
  `NodeNext`（Node 24 ESM）。**サーバ実行のためバンドルサイズは実質無関係**。

## 候補ライブラリ比較

| 観点 | zod 4（現状） | Valibot | ArkType |
|---|---|---|---|
| 設計思想 | メソッドチェーン `z.string().min(1).email()` | モジュラー＋パイプ `v.pipe(v.string(), v.nonEmpty(), v.email())` | TS 型リテラル風 `type({ name: "string>0" })` |
| バンドル(login schema 代表値) | 標準 ~17.7KB / Mini ~6.9KB | **~1.4KB**（最小） | ~40KB（パーサ/JIT を常時同梱） |
| ツリーシェイク | v4 で `zod/v4-mini` 追加（限定的） | **完全対応**（関数粒度） | 効きにくい（エンジン同梱型） |
| 実行性能 | 速い（v4 で大幅改善） | 速い（ArkType 寄り） | **最速**（JIT、zod 比 3-4x の報告） |
| 型推論 | `z.infer<T>` | `InferOutput<T>` / `InferInput<T>` | `typeof schema.infer` |
| エラー整形 | `z.prettifyError`, `issues[]` | `flatten` / `issues[]` | `summary` / `byPath` |
| 学習コスト | 低（普及・資料多） | 低〜中（パイプに慣れが要る） | **中〜高**（独自 DSL） |
| 成熟度/エコシステム | **最大**（事実上の標準） | 成長中・安定 | 新興・活発 |
| Standard Schema | 対応 | 対応（共同策定） | 対応（共同策定） |
| OpenAPI/JSON Schema | **`zod-openapi` が成熟** | `@valibot/to-json-schema`（OpenAPI は別途組立） | `schema.toJsonSchema()` 内蔵（OpenAPI は別途） |
| Vue / vee-validate | `@vee-validate/zod` | `@vee-validate/valibot` | Standard Schema 経由で利用可 |

### 補足: Standard Schema（移行リスクを下げる鍵）

zod / Valibot / ArkType の3つは**共通インターフェース Standard Schema を実装済み**。
`vee-validate` / `tRPC` / TanStack Form 等の下流ツールは Standard Schema 対応なら
**ライブラリ非依存**でスキーマを受け付ける。＝将来フロントで採用する際、フォーム連携の
adapter ロックインは小さい。

## このコードベースへの評価

### サーバ（`editor/server`）— 乗り換えの実利は薄い

- 代替勢の最大の売り＝**バンドル削減はサーバでは無意味**。性能も zod4 で実用上十分。
- `zod-openapi` 依存が重い。`Valibot` / `ArkType` へ移すと OpenAPI 生成系
  （`editor/server/src/openapi/schemas.ts`・`editor/server/src/openapi/document.ts`）を
  **別ツールで作り直し**になり、`.meta({ id })` による `#/components/schemas` 再利用や
  メタ付与の作法も置き換えが必須。移行コスト > 得られる利益。
- **結論: サーバは zod 4 を継続が妥当。**

### 将来のフロント（`editor/web` にクライアントバリデーション追加時）

- ここが代替勢の本領。**ブラウザ配布物のサイズが効く**ため:
  - バンドル最優先・フォーム中心 → **`Valibot`**（最小、`@vee-validate/valibot` で Vue 連携）。
  - 入力スキーマをサーバと共有したい → **Standard Schema 経由**でサーバ側 zod スキーマを
    そのままフロントのフォーム検証に流用する選択肢もある（重複定義の回避）。
- `ArkType` は型表現力・速度は魅力だが、独自 DSL の学習コストと ~40KB の下限が
  フロント用途では不利。サーバ用途でも `zod-openapi` 置換コストに見合わない。

### 総合推奨（このリポジトリ）

1. **当面は zod 4 を主軸として継続**（特にサーバ＋OpenAPI 連携）。
2. フロントにバリデーションを足す段階で、**そのレイヤだけ `Valibot` を検討**。
   下流連携は Standard Schema 前提で選ぶとロックインを最小化できる。
3. `ArkType` は「サーバの高速化が支配的要件になった」等の特殊事情が出たときの再評価対象。
