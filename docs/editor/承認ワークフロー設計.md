# 設計メモ: 編集タブの「精査者承認つき確定保存」ワークフロー

> 開発者向けの設計判断メモ。配布用 docx ではなく Markdown 正典として扱う。
> 起案日: 2026-06-29。対象: `editor/`（web / server / shared）。

## 1. 目的と要件

編集タブ（既存編集、`/edit/:id` query なし）で行った編集を、**精査者（承認者）の承認が
降りたときに限り実ファイル（`data/templates/<file>.html` + git）へ反映**する。承認前は
実ファイルを一切変更しない。承認画面では「どのような編集か」を**パーツ単位（行単位）の
変更前後プレビュー**で精査できるようにする。

確定済みの設計判断（合意済み）:

1. **精査者ロール** … 既存 `UserRole` に新ロール `approver` を追加（editor が申請、
   approver/admin が承認）。
2. **承認ゲートの対象範囲** … 編集タブの既存編集だけでなく、**作成タブの新規確定も含む**
   （実ファイルへ書く全経路を一律にゲートする）。
3. **申請データの保管** … **ファイル方式**（`data/reviews/`）。DB sproc は追加しない
   （既存方針「本体=ファイル/git、DB=台帳のみ」と整合、オフラインでも動く）。
4. **承認画面のプレビュー** … 既存の版比較（block diff）機構を流用し、**パーツ単位の
   行レイアウト**を既定ビューにする。

## 2. 現状（調査結果）

- 編集タブの編集は autosave で `data/drafts/<id>.{html,css}`（git 管理外）に下書き保存
  されるだけ。実ファイルへは触れない。
- 実ファイル反映の**唯一の関所**は、プレビュー画面（`/preview/:id`）の「確定保存」
  → `confirmSave`（`PUT /templates/:id`）→ `writeTemplateAndCss` + `commitAll`
  （`editor/server/src/repositories/templateRepo.ts` の `confirmSave`）。
- 既存ロールは `admin | editor | viewer` のみ。承認・ステータス・ワークフロー概念は
  未実装。`requireAuth` / `requireAdmin` ミドルウェアと監査ログ基盤（`auditedRethrow` /
  `logger.audit`）はある。
- 版比較機能（`editor/web/src/features/compare/`）が完成済み:
  - `compareService.renderVersionHtml` … 現行版（baseline=現公開テンプレ）を sample 値で
    nunjucks 描画。
  - `htmlBlockDiff.ts` … 各ページを「`.page` 直下 top-level block = **パーツ**」へ分解し、
    `rawKey`（`data-part-id`→id→class→tag）+ 出現順で前後を整列。**パーツごとに**
    `RenderedBlock { status, beforeHtml, afterHtml }`（着色済み）を生成している。
  - `CompareResultView.vue` … ページ左右並列・語句単位ハイライト（追加=緑/削除=赤/変更=赤帯）。
  - この整列キーは `partKey.ts`（編集画面のメモ・修正履歴のパーツキー）と**同一思想・同一キー**。

## 3. 設計の核

実ファイルへ書く処理（`writeTemplateAndCss` + `commitAll`）を**承認ハンドラ 1 本に集約**し、
`requireApprover` で施錠する。これにより編集者が API を直叩きしても物理的に実ファイルへ
書けない。確定保存は次の 2 段に割る:

- **申請（submit）** … 編集者が「確定保存」する代わりに、確定 HTML/CSS のスナップショットを
  `data/reviews/` へ積む。**実ファイル非更新**。
- **承認（approve）** … 精査者がパーツ単位の前後プレビューで確認し、承認したときに限り
  実ファイルへ反映する。

> **不変条件**: `writeTemplateAndCss`/`commitAll` を呼ぶ経路は `approve` ハンドラだけ。
> `requireApprover` で保護する。これが本設計のセキュリティ的な要。

## 4. ドメインモデル（`editor/shared/src/index.ts`）

```ts
export type UserRole = 'admin' | 'approver' | 'editor' | 'viewer';   // approver 追加
export type ReviewStatus = 'pending' | 'approved' | 'rejected';

export interface ReviewRequestMeta {
  id: string;                       // 申請ID
  templateId: string;
  attributes: TemplateAttributes;
  fundCode: string;
  origin: 'edit' | 'create';        // 編集タブ / 作成タブ 由来（2系統を保持）
  status: ReviewStatus;
  submittedBy: string;  submittedAt: string;
  reviewedBy: string | null;  reviewedAt: string | null;
  comment: string | null;           // 却下理由 / 承認メモ
  baseHash: string | null;          // 申請時点の現行版コンテンツキー（並行性警告に使う）
}
export interface ReviewRequest extends ReviewRequestMeta {
  html: string; css: string; filledHtml?: string;
}
export interface SubmitReviewRequest {
  templateId: string; html: string; css: string; fundCode: string;
  filledHtml?: string; origin: 'edit' | 'create';
```

## 5. サーバ側（`editor/server`）

| 追加/変更 | 内容 |
|---|---|
| `middleware/auth.ts` | `requireApprover`（`role==='approver' \|\| 'admin'`、他は 403）を追加。`requireAdmin` と同形。 |
| `files/reviewFiles.ts`（新規） | `data/reviews/<reqId>/{meta.json, body.html, body.css, filled.html}` を `atomicWrite`。一覧=readdir、状態更新=meta.json 書換。`templateFiles.ts`/`atomic.ts` と同流儀。 |
| `repositories/templateRepo.ts` | `confirmSave` の実書込部を `applyConfirmedSave(...)`（`writeTemplateAndCss` + git commit）として抽出。承認時に再利用。 |
| `repositories/reviewRepo.ts`（新規） | `submitReview`（pending 作成・**実ファイル非更新**・`baseHash` 記録）/ `listReviews(filter)` / `getReview` / `approveReview`（pending 検証→`applyConfirmedSave`→meta=approved）/ `rejectReview`（meta=rejected）。 |
| `routes/reviews.routes.ts`（新規） | 下表のとおり。承認/却下は `auditedRethrow('review.approve' / 'review.reject')`。 |
| `routes/templates.routes.ts` | 既存 `PUT /templates/:id`（直 confirmSave）を**撤去**（唯一の呼び元は PreviewView なので申請へ付け替える）。緊急直保存が要れば `requireApprover` 限定で別途用意。 |

ルート一覧:

| メソッド・パス | preHandler | 役割 |
|---|---|---|
| `POST /review-requests` | `requireAuth`（viewer 不可） | 申請を作成（pending） |
| `GET /review-requests?status=` | `requireAuth` | 承認者は全件、編集者は自分の申請のみ |
| `GET /review-requests/:reqId` | `requireAuth` | 申請詳細（body 込み・プレビュー用） |
| `POST /review-requests/:reqId/approve` | `requireAuth, requireApprover` | 実ファイル反映 + git commit |
| `POST /review-requests/:reqId/reject` | `requireAuth, requireApprover` | 却下（理由付き） |

- **git コミットメッセージ**: `確定保存(承認): <id> 申請=<submitter> 承認=<approver>`。
  `Co-Authored-By` で申請者も残す。
- **自己承認ポリシー**: 既定で `submittedBy === reviewedBy` を拒否（職務分掌）。`admin` のみ例外可。

## 6. Web 側（`editor/web`）

- **承認画面**（新規）`ReviewDiffView.vue`: §7 のパーツ単位プレビュー + 承認/却下（理由入力）。
- **api/rest/reviewRepo.ts・api/local/reviewRepo.ts**（新規）: rest=API、local=localStorage
  ミラー（オフラインデモ用、ロール強制なし）。`api/repositories.ts` に結線。
- **MainLayout / メニュー**: approver・admin に「承認待ち」導線（pending 件数バッジは任意）。
- **EditTabView の一覧**: テンプレごとに `申請中 / 承認済 / 却下` を表示し、編集者が自分の
  申請状態を追えるようにする。

## 7. 承認画面のプレビュー（パーツ単位＝行レイアウト）

### 7.1 既存 block diff の per-part 結果を行として取り出す

パーツ単位の差分は **既に計算済み**。`renderBlock()` がパーツごとに着色済み前後 HTML を
生成しているが、`diffPage()` がページ単位に連結して捨てている。そこを surface する**追加変更
のみ**で実現する。

```ts
// editor/web/src/features/compare/htmlBlockDiff.ts
export interface DiffBlock {
  key: string;            // 既存: rawKey#出現順（= パーツ安定キー、partKey と同系）
  status: BlockStatus;    // 既存: same | changed | added | removed
  beforeHtml: string;     // 追加: このパーツだけの着色済み before
  afterHtml: string;      // 追加: このパーツだけの着色済み after
  label: string;          // 追加: 「ページN・パーツM」（partLabelMap と同採番）
}
```

`diffPage()` は既に `rendered: Map<key, RenderedBlock>` を持つので、各 `DiffBlock` へ
`beforeHtml`/`afterHtml` を移すだけ。ページ単位の連結文字列は既存 `CompareResultView` 用に
残し**後方互換・低リスク**にする。

### 7.2 `ReviewDiffView.vue`（パーツ行レイアウト）

ページ左右並列ではなく、**パーツ＝1 行**の縦リスト:

- 既定は `status !== 'same'` のパーツのみ（変更/追加/削除）。「変更なしも表示」トグルあり。
- 各行: ヘッダ「**ページN・パーツM**」＋ステータスバッジ → そのパーツだけを `srcdoc`
  iframe で **変更前 | 変更後** の 2 ペイン表示。
- 着色は既存 `HIGHLIGHT_CSS`（追加=緑下線/削除=赤下線/変更=赤帯）と iframe 自動フィット
  （`fitFrame`/`ResizeObserver`）を流用。
- 画面端に **承認 / 却下（理由入力）** アクション。

```
変更パーツ 3件（変更2 / 追加1 / 削除0）          [変更なしも表示 ▢]
─────────────────────────────────────────────
ページ1・パーツ2  〔変更〕   [ 変更前 ⟦…⟧ | 変更後 ⟦…緑/赤下線…⟧ ]
ページ2・パーツ1  〔追加〕   [   （なし）  | 変更後 ⟦…緑帯…⟧       ]
ページ3・パーツ4  〔変更〕   [ 変更前 ⟦…⟧ | 変更後 ⟦…⟧            ]
─────────────────────────────────────────────
                                  [ 却下（理由） ]  [ 承認する ]
```

### 7.3 データ経路（presentation だけ差し替え）

```
現行版(before) = compare.renderVersionHtml('baseline:' + templateId)        // 現公開版
申請版(after)  = compare.renderTemplateBody(review.html, review.css, fundCode) // 申請内容
diff           = htmlWorker.buildHtmlDiff(beforeHtml, afterHtml, cssBefore, cssAfter)
                 → diff.pages[].blocks[] を全ページ横断で flat 化 → パーツ行リスト
```

diff 計算は `CompareView` と完全共有。`compareService` に **任意本文を同一描画経路で描く
公開 API `renderTemplateBody(html, css, fundCode)`** を追加（baseline/snapshot が内部で使う
「sample 取得 + `renderJinja`」を抽出）。現行版・申請版を同一描画経路にし、見せかけ差分を出さない。

### 7.4 採番・整合の利点

行ラベルは `partLabelMap` と同じ「ページN・パーツM」採番。diff の整列キーが編集画面の
パーツキー（メモ・修正履歴の紐付けキー）と**同一**なので、承認画面の「ページ2・パーツ3 を
変更」行は編集者側の同じパーツと一致する。承認と編集が同じパーツ語彙で揃う。

### 7.5 留意点

- **追加/削除パーツ**: `added` は前ペイン空、`removed` は後ペイン空。採番は after 側基準、
  削除パーツは別枠採番。
- **ページ跨ぎ移動**: パーツがページを跨いで動くと削除＋追加に見える（compare と同程度の
  best-effort）。承認用途では実害小。
- **ページ単位ビューの併存（任意）**: 既存 `CompareResultView`（ページ左右並列＋ページずらし）
  を「ページ表示」トグルとして残し、既定を「パーツ表示」にできる。長い帳票の俯瞰用の保険。

## 8. 描画整合・並行性

- diff は **Jinja 再描画ベース**（現行版・申請版とも同一 sample で `renderJinja`）。申請が持つ
  `filledHtml`（値差込済み成果物）は、必要なら別タブ「成果物プレビュー」の補助表示に留め、
  見せかけ差分を避ける（compare 既存の不変条件を踏襲）。
- **ベース不一致の警告**: 申請時に現行版コンテンツキーを `baseHash` に保存。承認時に現行と
  不一致なら「申請後にベースが更新されています。再申請を推奨」と警告（強制ブロックはしない）。
  並行承認で現行版が動いた場合の取り違えを防ぐ。
- **「承認前」の基準版**: 現行のライブ公開版を既定（承認したら今のファイルにこの変更が乗る、を
  忠実に表現）。陳腐化は `baseHash` 警告でカバー。

## 9. 2 系統の原則（CLAUDE.md）順守

承認ゲートは**実ファイル反映のタイミングのみ**を制御する。`SubmitReviewRequest.origin` で
編集経路（`tpl.filled`・ハイライト無し）／作成経路（`toFilled`・ハイライト有り）の区別を
申請に保持する。`confirmSave` のレンダリング/Jinja 復元・値源・ハイライト判定
（`route.query.created`）には一切手を入れない。

## 10. 監査・履歴

- 監査イベント `review.submit` / `review.approve` / `review.reject` を `logger.audit` で記録。
- 確定保存の edit-history エントリは **承認時**に積む（申請時ではない）。
- git コミットに申請者・承認者の双方を残す（§5）。

## 11. テスト（CI 必須）

- server: `submit→pending`（`data/templates` 非更新を断言）/ `approve→ファイル書込+git
  commit+meta=approved` / `reject→rejected` / 編集者の approve は 403 / 自己承認拒否。
- web: local reviewRepo ラウンドトリップ / PreviewView のロール別ボタン / 承認キュー絞り込み。
- diff: `htmlBlockDiff` のパーツ単位前後 HTML 出力 / added・removed 行 / ラベル採番
  （`partLabelMap` 一致）。
- 既存の 2 系統ガードテストを緑のまま維持。

## 12. 設定・配布・移行

- `config.requireApproval`（rest 既定 ON）でフラグ化。`requireAuth=false` のローカルモードでは
  強制力が無い旨を明記（本番=rest/phase2 で有効）。
- `gen-seed` に approver ユーザを 1 名追加（デモ用）。
- 既存 `PUT /templates/:id` 撤去に伴い、呼び元（PreviewView/templatePreviewService.confirmSave）を
  申請へ付け替え。
- `docs/editor/src/操作手順書.md` に「申請→承認→反映」フローを追記（md→docx 生成系で再生成）。

## 13. 実装順（PR 分割の目安）

1. **shared** … 型（`ReviewRequest*` / `approver`）・api-paths・`ReviewRepository` 契約。
2. **server** … `reviewFiles` / `reviewRepo` / `requireApprover` / `reviews.routes`、
   `applyConfirmedSave` 抽出、`PUT /templates/:id` 撤去。
3. **web データ層** … rest+local `reviewRepo`・ロール配線・`api/repositories` 結線。
4. **diff 拡張** … `htmlBlockDiff` の `DiffBlock` 拡張、`compareService.renderTemplateBody`。
5. **web 画面** … `ReviewDiffView`（パーツ行）+ `ReviewQueueView` + PreviewView 申請化 +
   メニュー導線 + 一覧の状態表示。
6. **仕上げ** … seed approver・監査イベント・テスト・操作手順書更新。
