# editor Adobe Reader 風コメント機能 — dig 調査記録

- 日付: 2026-09-03
- 対象: editor 編集タブ・承認画面へのコメント機能(メモ UI・検索・絞り込み)追加
- 状態: **完了**(Round 3 で全論点確定。次は brainstorming → writing-plans)

## 既存資産(前提)

- パーツメモ = 追記型スレッド(`PartNoteEntry`、アンカー `pathKey`、交付版⇄全体版で共有、
  基準日で分断)。表示 = canvas 吹き出し(`NoteBubble.vue`)/ 追加 = 右ペイン(`Inspector.vue`)。
- 承認画面 `ReviewDiffView` はメモを表示しない。承認者コメントは申請単位 `comment` 1 本。
- 承認画面の入口: 精査キュー(`/reviews`)に加え、編集タブ一覧の承認待ちバッジ
  (`EditTabView.openReview`)と `EditorTopBar` の承認待ちバッジからも `review-detail` へ遷移可能
  (同一テンプレに申請が 2 件以上のときのみキューへ倒す)。
- 組版比較は opaque iframe(`PreviewPanel`)。親が文書 HTML を組み(`reviewCompareDocs.wrapDoc`)
  子へ送る。`.page` 1 要素 = 1 印刷ページの前提で変更ページマーカーを文書内へ注入している。

## Round 1 決定

| 論点 | 決定 | 根拠 | リスク |
|---|---|---|---|
| 既存メモとの関係 | 置換(既存パーツメモを Adobe 風コメントへ発展、UI 刷新) | 入口 1 つ・データ 1 系統 | 吹き出し設計の作り直し・移行 |
| 承認画面の入口 | 精査キュー `/reviews` 一覧を廃止。承認者も編集タブからテンプレを開いて承認画面へ | 1 テンプレ = 1 PDF の文脈統一 | 「申請待ち一覧」の代替が要る |
| アンカー単位 | ページ座標(ページ番号 + x/y) | Adobe の付箋と同じ操作感 | 編集で座標がずれる / ペア共有 |

## Round 2 決定

| 論点 | 決定 | 根拠 | リスク |
|---|---|---|---|
| アンカー | **ページ座標を撤回し、現行 `pathKey`(パーツ構造キー)に戻す** | 編集でのずれ・ペア共有不能を避ける。既存データ互換 | パーツ内の語句は指せない(許容) |
| ペア版種共有 | **交付版⇄全体版のマージ共有を廃止** | データを版インスタンス単位に単純化 | 2026-09-01 設計の撤回。相手版の投稿が見えなくなる(Round 3 で扱い決定) |
| 承認タブ | 「承認」タブは残す。中身は精査キュー一覧ではなく**編集タブで直前に選んだテンプレ 1 件の承認画面へ直遷移**。1 件ずつ承認 | 1 テンプレ = 1 PDF の文脈 | 記憶方法・申請なし時・複数申請・承認後の遷移先(Round 3) |
| 承認可否との関係 | 独立(コメントは注釈。承認・差し戻し・保留は現行の `comment` 1 本 + ボタン) | `applyConfirmedSave` の関所・監査に触れない | — |

### Round 2 で調べた事実(採用案の裏付け)
- ページ座標案は技術的には成立した(`.page` 1 要素 = 1 印刷ページ、mm 正規化、承認側は
  `reviewCompareDocs.wrapDoc` でピンを文書内注入)が、編集でのずれ・ペア不能を理由に不採用。
- 承認画面への編集タブ導線は既に存在: `EditTabView.openReview`(一覧の承認待ちバッジ)と
  `EditorTopBar` の承認待ちバッジ → `review-detail`。同一テンプレ複数申請時のみキューへ倒す分岐あり。
- タブ復帰は `stores/tabMemory.ts`(タブ → 直前 fullPath、in-memory)。承認待ちは
  `stores/pendingReviews.ts`(`byTemplate`、pending+held)。

## Round 3 決定(最終)

| 論点 | 決定 | 根拠・補足 | リスク |
|---|---|---|---|
| コメント構造 | **Adobe 準拠**: 投稿に `status: 'open'\|'resolved'` + `replyTo`(親投稿 id、任意)+ `kind`(種別。例: `note`/`fix-request`/`question`) | 絞り込み軸(種別・未返信)を持つ | 入れ子表示・親削除時の孤児規則・上限の数え方(返信込み)を仕様で決める |
| 寿命 | 版インスタンス(`templateId`)に永続。承認後も残る。基準日をまたがない | 現行と同じ | — |
| 権限 | 現行維持(全ロールが追加・編集・削除可。解決切替も同様) | — | viewer も書ける点は現行踏襲 |
| 検索範囲 | 開いているテンプレ 1 件内。クライアント側フィルタ(著者/日付/状態/種別/パーツ/本文) | API 追加なし | 1 テンプレ最大 1000 pathKey × 200 投稿でも client filter で足りる想定 |
| 承認タブの記憶 | 編集画面を開いた id(`tabMemory` の `edit` 直前画面が `/edit/:id`)。**開いていなければ承認タブはメッセージで「編集タブからテンプレを開く」よう促す** | 新ストア不要 | 一覧で行を選んだだけでは対象にならない(仕様) |
| 申請が無いテンプレ | 空状態「承認待ちの申請がありません」+ 編集タブへ戻る導線 | — | — |
| 同一テンプレ複数申請 | **禁止しない**。承認タブはそのテンプレの承認待ち申請(pending+held)を**全部 1 画面に縦に並べる**(申請ごとに変更前/後の比較 + 承認/差し戻し/保留ボタン。決着は申請 1 件ずつ) | ユーザーの「一括申請」= 1 PDF に対する複数申請のまとめ表示・承認の意(一覧からの一括提出は無い) | 複数の組版比較 iframe(申請数 × 2)の負荷。`ReviewDiffView` をセクション component 化する |
| 決着後の遷移 | 同じ画面に留まり、決着した申請のセクションは決着済み表示へ。全件決着で「編集タブへ戻る」導線 | — | — |
| 既存メモの移行 | ファイル形式据え置き(`notes/<templateId>.json` の `Record<pathKey, 投稿[]>`)。`status`/`replyTo`/`kind` は任意フィールドで足し読み取り時に既定値補完(`open`/なし/`note`)。ペア相手版の投稿は見えなくなる(ファイルは残す) | 移行ゼロ。ロック・4MB 上限・`readNotesStrict` を温存 | 交付版⇄全体版で投稿が消えて見える点を手引きで説明 |

## 撤回・却下(再提案しない)

- ページ座標アンカー(Round 1 で選び Round 2 で撤回): 編集で座標がずれ、ペア版種で共有不能。
  技術的には `.page` mm 正規化 + `wrapDoc` 注入で成立するが採らない。
- 交付版⇄全体版のメモ共有(2026-09-01 設計): 廃止。読み取りマージ経路を残す C 案も不採用。
- 精査キュー一覧(`/reviews` の一覧画面): 廃止。承認タブは 1 テンプレの承認画面へ直遷移。
- 未解決コメントによる承認ブロック(強い連動): 不採用。コメントは注釈で、関所には触れない。
- 申請中の再申請禁止(409): 不採用。複数申請は 1 画面縦並びで受ける。
- 全テンプレ横断のコメント検索 API: 不採用(1 テンプレ内のクライアント側フィルタ)。

## 残リスク(計画時に扱う)

1. 承認タブの複数申請縦並び: iframe 数が申請数 × 2 になる。ラップ表示(折りたたみ・遅延組版)の要否。
2. `replyTo` の親削除・上限(1 パーツ 200 投稿は返信込みで数える想定)・`legacy:` id との整合。
3. 承認タブへの直遷移で `pendingReviews.byTemplate` の鮮度(承認画面直後の refresh 契機)。
4. `EditTabView.openReview` / `EditorTopBar` 承認待ちバッジの遷移先を承認タブ(テンプレ id 基準)へ揃える。
   `review-detail`(`/reviews/:reqId`)ルートは廃止か、承認タブへリダイレクトするかを計画で決める。
5. 手引き・設計書・設計正典(「パーツメモは…ペア版種と共有する」「精査キュー」記述)の更新。
6. UI 幅: 編集画面の右ペイン 312px にコメント一覧 + 検索/絞り込みを収める。ヘッダに要素を足すなら実測。
